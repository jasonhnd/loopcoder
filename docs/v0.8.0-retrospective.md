# v0.8.0 Engineering Retrospective

Status: historical process record
Date: 2026-07-16
Scope: v0.8.0 design, implementation, self-hosting hardening, and release
candidate work

## Summary

LoopCoder v0.8.0 substantially expanded the delivery engine: durable
DeliveryRun records, provider and model inventory, quota-aware routing,
progress delivery, detached supervision, nested-agent governance,
cross-provider handoff, and a macOS Apple Silicon release contract.

The product work converged, but the development process did not stay bounded.
The version accumulated too many coupled objectives, self-hosting defects
amplified recovery cost, full verification was repeated at too many layers,
delivery-only failures triggered unnecessary recomputation, and local resource
use had no hard governor. A long-running self-hosting session eventually made a
local development host unresponsive and required a restart.

The incident was not evidence that rigorous verification is unnecessary. It
showed that verification, recovery, reporting, and local execution require the
same explicit budgets and state machines as provider work.

## Release-State Terminology

Three states were repeatedly confused during the work:

| State | Meaning |
| --- | --- |
| Code-complete | The planned behavior exists in reviewed code and its implementation PR checks pass. |
| Candidate-complete | A protected `main` SHA has passed integrated CI and is the sole input to a staged release. |
| Release-complete | The exact staged artifact has passed signing, checksum, install, upgrade, migration, rollback, and publication verification and is publicly available. |

A code-complete repository is not a release. A green source CI run is not proof
that a packaged artifact installs, reports the right version, migrates real
state, or can be rolled back.

## Scope That Entered v0.8.0

The initial roadmap grouped work under the public v0.8.0 roadmap and epics,
including issues [#714](https://github.com/jasonhnd/loopcoder/issues/714)
through [#744](https://github.com/jasonhnd/loopcoder/issues/744). The major
domains were:

- DeliveryRun, task, decision, approval, and override contracts;
- provider installation, account-readiness, and model inventory;
- quota windows, usage, budgets, availability, and circuit breakers;
- task classification, bounded decomposition, and explainable routing;
- provider-neutral Soul, Tera, and Luna role envelopes;
- policy profiles, pins, fallback, replanning, and verification councils;
- provider-native sub-agent registration, scope, one-writer ownership,
  cancellation, and recovery;
- host capability negotiation and progress delivery;
- Codex, Claude Code, Paseo-style, Grok, Antigravity, and experimental Gemini
  integration boundaries;
- cross-provider handoff and side-effect receipt reconciliation;
- deterministic simulation and evaluation scenarios; and
- public release, migration, and self-bootstrap acceptance.

Late hardening added durable provider ownership, detached supervision,
provider-free waits, and orchestration cost controls under
[#959](https://github.com/jasonhnd/loopcoder/issues/959) and children
[#960](https://github.com/jasonhnd/loopcoder/issues/960) through
[#968](https://github.com/jasonhnd/loopcoder/issues/968).

That was too much for one minor release. Each domain was individually
reasonable; their simultaneous integration created a wide state, migration,
host, provider, and release blast radius.

## Timeline by Engineering Phase

This timeline is intentionally phase-oriented. It avoids private session
details and uses public repository artifacts as the durable record.

### Phase 1: Contract freeze

The project correctly started by freezing the v0.8 contracts before runtime
implementation:

- DeliveryRun contracts:
  [`specs/0801-delivery-run-contracts.md`](specs/0801-delivery-run-contracts.md)
- provider inventory:
  [`specs/0802-provider-inventory.md`](specs/0802-provider-inventory.md)
- quota, usage, budget, and availability:
  [`specs/0803-quota-usage-budget.md`](specs/0803-quota-usage-budget.md)
- decomposition and routing:
  [`specs/0804-decomposition-routing.md`](specs/0804-decomposition-routing.md)

- threat model:
  [`specs/0742-v080-security-threat-model.md`](specs/0742-v080-security-threat-model.md)

This phase reduced semantic ambiguity, but several individual specs were large
enough to create broad implementation issues.

### Phase 2: Core implementation waves

Implementation added the durable data model, planner, routing, provider
inventory, quota collection, Grok adapter, agent registration, progress
receipts, host negotiation, and handoff paths.

The work produced many valuable bounded components, but integration cost grew
because components shared:

- SQLite schema and transaction semantics;
- provider execution and recovery;
- host progress delivery;
- model and quota evidence;
- task and plan fingerprints;
- child-run lifecycle; and
- common CLI and test packages.

The repository's public Git history from v0.7.0 to v0.8.0 is the authoritative
implementation sequence. This retrospective intentionally does not copy local
worker transcripts or machine-local reports into Git.

### Phase 3: Runtime hardening from self-hosting evidence

Self-hosting exposed defects that ordinary unit implementation had not fully
covered:

- silent-but-healthy providers were mistaken for stalled providers;
- failed attempt artifacts raced with cleanup;
- environment leakage affected Git fixtures;
- detached provider authority needed durable process identity;
- supervisor death needed an OS-specific guardian and process-group reaping;
- recovery needed to reconcile a live provider before redispatch;
- waits needed to survive restart without provider polling; and
- orchestration calls and token overhead needed a durable budget.

The hardening work was valid and improved product safety. The process problem
was that it entered the same release as the original feature set instead of
being planned as a bounded stabilization phase with explicit stop conditions.

### Phase 4: Platform contraction

The release surface was reduced to native `darwin/arm64`. This was a good scope
decision because it removed Windows, Linux, WSL, Intel macOS, Rosetta, and
container runtime matrices from v0.8.0.

The accepted platform contract is
[`specs/0884-macos-arm64-only.md`](specs/0884-macos-arm64-only.md).
The contraction reduced the release matrix, but it happened after substantial
cross-platform work and did not by itself reduce repeated local verification.

### Phase 5: Release-candidate hardening

The release path added:

- four stable protected checks: `verify`, `test`, `race`, and `security`;
- a deterministic full-race gate before packaging;
- a single macOS arm64 archive;
- one signed `SHA256SUMS` manifest;
- a diagnosable draft release;
- staged-artifact install and self-bootstrap smoke;
- a real v0.7.0 schema-9 to v0.8 schema-30 migration;
- verified backup and rollback opened by the prior release; and
- a protected human publication environment.

This is the correct release architecture. See
[`reference/releasing.md`](reference/releasing.md) and
[`reference/self-bootstrap.md`](reference/self-bootstrap.md).

### Phase 6: Staged release smoke found a wire-contract defect

The candidate built, signed, and staged its intended assets. The release smoke
successfully migrated a real prior-version database, then failed while reading
the JSON response because the nested health object emitted Go-style field names
instead of the documented snake_case wire contract.

Issue [#997](https://github.com/jasonhnd/loopcoder/issues/997) narrowed the
correction to explicit JSON tags and a raw CLI JSON regression test. This was a
real release blocker because the public CLI contract and release smoke
disagreed.

The positive lesson is that artifact-level smoke caught a defect source CI had
not exposed. The negative lesson is that the release path had already paid a
large full-matrix cost before the wire-contract check failed.

### Phase 7: Local resource exhaustion

During continued release orchestration, several expensive or persistent
activities overlapped on the local development host:

- full or large Go test invocations;
- race-detector work;
- pre-push verification that repeated remote checks;
- provider Worker and Verifier processes;
- shell or CLI status watchers;
- retained worktrees and application host processes; and
- repeated recovery after delivery-stage failures.

The workflow had token budgets and provider-call accounting, but no binding
aggregate CPU, memory, process-count, process-tree lifetime, or local-test
concurrency budget. The local host became unresponsive.

This is the main operational incident recorded by this retrospective.

## What Consumed Time

The long calendar time did not represent continuous useful implementation.
Significant time was spent in the following categories.

### Repeated verification

Substantially overlapping checks ran at Worker, local pre-push, conductor,
Verifier, PR, promotion PR, integrated `main`, release build, and release-smoke
layers.

Verification should be layered by purpose. Repeating a full suite at every
boundary does not multiply confidence proportionally; it multiplies queue,
compute, and failure-surface cost.

### Coarse-grained retries

Push timeout, PR creation, report delivery, CI waiting, and provider execution
were not always treated as independent resumable stages. When a late delivery
stage failed, completed implementation and verification could be recomputed.

### Non-deterministic or oversized test gates

Race-detector timing amplified tests that used wall-clock assumptions or large
stress loops. A package-level timeout could appear to implicate the feature
under test even when the true problem was aggregate test duration or fixture
contention.

### Serial dependency chains

Some release blockers correctly depended on prior storage or lifecycle work.
The combined chain meant every retry delayed all downstream work. Large issues
made individual attempts long and made partial progress harder to preserve.

### Invisible waiting

When a host showed only a running process, pending CI, or generic thinking
state, the user could not distinguish useful progress from waiting, retrying,
or a stuck child. This increased manual status checks and encouraged additional
watchers.

## Root-Cause Analysis

### Root cause 1: Release scope exceeded a bounded minor version

The roadmap combined multiple platform capabilities and their stabilization
work. There was no enforceable issue-count, dependency-depth, or expected
attempt-duration ceiling.

### Root cause 2: Self-hosting recursion lacked a separate risk policy

LoopCoder was both the tool performing work and the product being modified.
A defect in dispatch, supervision, report delivery, recovery, or worktree
management could invalidate the mechanism responsible for fixing that defect.

Self-hosting must therefore use stricter concurrency, checkpoint, and rollback
rules than an ordinary consumer repository.

### Root cause 3: Failure types were not first-class orchestration states

Implementation, test, provider, delivery, infrastructure, waiting, and human
decision failures need distinct durable outcomes and recovery entry points.
Without that distinction, late failures restart early work.

### Root cause 4: Verification was organized by actor, not by evidence need

Each actor attempted to be safe independently. Worker, conductor, verifier, Git
hooks, CI, and release automation each ran checks without one owner deciding
which layer already supplied the required evidence.

### Root cause 5: Release freeze was advisory rather than mechanical

The process did not enforce a hard transition from feature development to
release-candidate stabilization. New findings could continue to expand the
candidate indefinitely.

### Root cause 6: Progress generation and user visibility were different

Durable progress receipts existed, but generation, transport, visibility, and
acknowledgment are separate states. A receipt in storage did not guarantee that
the active host showed a useful update.

### Root cause 7: Cost accounting omitted host resources

The v0.8 orchestration cost budget in
[`specs/0968-orchestration-cost-budget.md`](specs/0968-orchestration-cost-budget.md)
accounts for model calls, reported tokens, waits, retries, duplicate
suppression, and context bytes. It does not govern aggregate host CPU, memory,
swap, process count, test parallelism, or process-tree lifetime.

That omission allowed a run to remain within provider budget while exhausting
the machine executing it.

## Process Defects versus Product Defects

| Category | Examples | Release treatment |
| --- | --- | --- |
| Product contract defect | Incorrect JSON field names, unsafe migration, duplicate provider execution | Fix when P0/P1 or release-contract blocking. |
| Product edge defect | Low-risk alias leniency, cosmetic output, optional unsupported integration | Defer unless it violates a public promise. |
| Process defect | Duplicate full tests, unbounded watcher, whole-task retry after push failure | Fix the playbook and orchestration policy; do not repeatedly rewrite product code. |
| Infrastructure defect | Runner queue, transient GitHub failure, local network timeout | Preserve completed work and resume only the failed stage. |
| Evidence gap | Missing report visibility, ambiguous external side effect | Fail closed to `needs-human`; do not invent success or automatically re-execute. |

This classification prevents every operational problem from becoming another
product feature in the release candidate.

## What Worked Well

Several controls materially improved the release and should remain.

### Contract-first implementation

The five phase specs made lifecycle, authority, migration, capability,
confidence, routing, and federation rules reviewable before code.

### Machine-local state isolation

Registered project runtime state moved outside the repository, reducing
accidental publication risk and allowing multiple projects and workspaces to
share durable history.

### Claim, lease, heartbeat, and fencing semantics

Nested execution and recovery now have explicit ownership generations. Stale
owners cannot overwrite a later owner's completion, and ambiguous external
execution fails closed.

### Provider-free deterministic waits

Issue [#967](https://github.com/jasonhnd/loopcoder/issues/967) established
restartable local waiting for CI, approval, quota reset, outbox delivery, and
worker terminalization without spending provider quota.

### Orchestration token budget

Issue [#968](https://github.com/jasonhnd/loopcoder/issues/968) made provider
calls and orchestration token overhead visible and bounded. The contract needs
a host-resource companion, but its fail-closed accounting model is sound.

### Staged draft release

Build once, sign once, stage a draft, smoke the exact archive, then publish
after a protected human environment gate is the right release design.

### Real predecessor migration and rollback

Using the published v0.7.0 binary to create real predecessor state provided
evidence that synthetic fixtures alone could not provide.

## Immediate Corrections Applied

- Freeze v0.8.0 against new features.
- Limit the final JSON correction to the release-contract defect.
- Move full and race verification to GitHub-hosted macOS runners.
- Stop local Worker, Verifier, full-suite, and persistent watcher execution
  during release closeout.
- Distinguish feature completion from release publication.
- Preserve the failed draft and workflow evidence for diagnosis.
- Record this retrospective and route future self-hosting through a mandatory
  playbook.

## Corrective Actions for the Next Patch Cycle

These are follow-up engineering controls. They must be split into small issues
and must not expand the frozen v0.8.0 release.

| Priority | Control | Intended result |
| --- | --- | --- |
| P0 | Local host resource governor | Bound aggregate CPU, RSS, process count, parallel tests, and process-tree lifetime. |
| P0 | Delivery-stage resume | Retry push, PR creation, report delivery, or status publication without re-running a successful provider. |
| P0 | Mandatory progress visibility | Surface a bounded five-minute status packet through every supported host path. |
| P1 | Verification evidence planner | Select the minimum required test tier once per boundary and suppress duplicate full checks. |
| P1 | Worktree and orphan-process janitor | Reconcile stale registrations, retained worktrees, and verified orphan process groups. |
| P1 | RC freeze state | Prevent new feature issues from joining an active release candidate. |
| P1 | Bounded candidate policy | Stop automatic repair after two failed candidates and require a human GO/NO-GO decision. |
| P2 | Historical performance ledger | Compare useful implementation time with waiting, retry, verification, and delivery overhead. |

## Success Measures

The next self-hosted version should satisfy measurable process outcomes:

- no local full-suite or full-race execution by default;
- no more than one local provider process at a time;
- no provider call for deterministic waiting, polling, heartbeat, reporting, or
  delivery retry;
- no repeated provider call after a verified implementation commit exists;
- a user-visible status at least every five minutes for active work;
- every retry classified by stage and limited to one automatic retry;
- every issue small enough for a bounded attempt;
- no more than two release candidates without human re-scoping;
- zero unowned child processes after cancellation or completion; and
- one evidence matrix that proves release completion.

## Final Learning

Automation becomes dangerous when capability grows faster than budgets,
stopping rules, and observability.

The goal of the next process is not fewer safeguards. It is one bounded,
non-duplicated safeguard at the correct layer, with durable evidence and a
clear owner.
