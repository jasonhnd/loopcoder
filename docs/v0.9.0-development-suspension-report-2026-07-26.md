# LoopCoder v0.9.0 Development Suspension Report

**Decision date:** 2026-07-26  
**Report prepared:** 2026-07-27  
**Decision:** Development stopped by the owner  
**Release decision:** `NO_GO` / `NOT_RELEASED`  
**Project state:** Suspended until a new, explicit owner decision  
**Last public release:** `v0.8.1`  
**Exact stopped `pre-prod` SHA:** `30cabdaf77d749c8305349f7f6a87189014b8af8`  
**Last internal candidate:** `0.9.0-rc.61`, draft-only, never accepted  

> This is the authoritative project-stop record for the v0.9.0 development
> cycle. It supersedes any implication in candidate quickstarts, capability
> matrices, issue closure, pull-request checks, integration runs, release
> candidate workflow results, or agent summaries that v0.9.0 was complete or
> ready to publish.

## 1. Executive Verdict

LoopCoder v0.9.0 did not meet its product acceptance objective. The owner
therefore stopped the project after a prolonged development and validation
cycle.

The cycle produced a large amount of real engineering work:

- a new storage and authority model;
- provider inventory, account, model, depth, and quota observation paths;
- policy-driven auto-routing;
- bounded WorkGraph orchestration;
- capacity reservation and reconciliation ledgers;
- interruption, recovery, reroute, and integration evidence;
- reports, support bundles, migration paths, packaging, and qualification
  machinery;
- 230 pull requests merged into `pre-prod` during the formal v0.9 merge window;
- 59 successful internal release-candidate build runs, reaching `rc.61`;
- real Codex and Claude executions in a private disposable repository;
- one forced-restart flow, one deliberately unavailable route, and real pull
  requests reaching a human merge gate.

Those facts are not the same as product completion.

The required final proof was one exact, newly built draft archive whose
downloaded binary, digest, manifest, and `pre-prod` SHA were bound together,
followed by a fresh live consumer canary that:

1. turned one real goal into at least four useful, transparent children;
2. routed real work through at least two provider companies and at least two
   model/depth levels based on fresh account observations;
3. recorded truthful capacity before, reserved, actual, and after values;
4. excluded or retried an unavailable route without duplicate work;
5. survived exactly one forced restart within resource ceilings;
6. reached a real pull request and human gate;
7. emitted credential-safe universal reports; and
8. passed the exact-artifact qualifier with every required metric `pass` and
   `not_run=0`.

That proof never existed.

The nearest attempt, `rc.60`, reached a real pull request with required checks
green, but the exact-artifact qualifier returned `NO_GO`. Its raw evidence
validation found missing and inconsistent capacity evidence, could not accept
the unavailable-route retry, could not validate restart ceilings, and marked
six required product metrics `not_run`. The subsequent `rc.61` archive was
built successfully, but the owner stopped development before its live consumer
canary or qualifier began. It is therefore an unaccepted archive, not a release
candidate in the product sense.

The central failure was not one remaining defect. The product runtime, provider
truth model, recovery model, evidence schema, and qualifier were all still
changing together. Each newly exposed production defect caused another code
change, merge, exact-SHA integration run, archive, and canary. Every fix also
invalidated the previously tested artifact. The process optimized for fixing
the next observed defect, but it did not prove convergence or protect the
owner's time with an effective stop-loss rule.

The correct final status is:

| Question | Answer |
| --- | --- |
| Was meaningful code produced? | Yes |
| Did narrow tests and CI often pass? | Yes |
| Were exact draft archives built? | Yes |
| Did real providers execute useful work? | Yes, in partial and failed acceptance attempts |
| Did a real PR reach a human gate? | Yes, during `rc.60` acceptance |
| Did an exact archive pass the complete live qualifier? | No |
| Was v0.9.0 tagged or publicly released? | No |
| Should any v0.9 candidate be installed as a supported release? | No |
| Is development active? | No |

## 2. Owner Decision and Meaning of "Stopped"

On 2026-07-26, the owner explicitly directed the project to stop development
because the requested product outcome had not been achieved after an
unacceptably long cycle.

For this repository, "stopped" means all of the following:

- no additional v0.9 feature implementation;
- no continuation agent;
- no new issue, worktree, branch, or pull request for v0.9 product work;
- no rerun of the private acceptance canary;
- no new release-candidate archive;
- no merge intended to advance v0.9;
- no public `v0.9.0` tag;
- no GitHub release publication;
- no claim that issue closure, source tests, CI, or archive creation constitutes
  product acceptance;
- preservation of the exact stopped state and its evidence for a possible
  future, separately authorized decision.

This report is documentation of the stop. It is not a new roadmap and does not
authorize resumption.

## 3. Report Scope and Evidence Rules

This report covers the v0.9 architecture, implementation, merge, release
candidate, and live acceptance effort through the owner's stop.

The formal v0.9 merge window began with the roadmap PR merged on 2026-07-20 and
ended at the stopped `pre-prod` SHA on 2026-07-26. The owner described the
broader uninterrupted delivery effort, including the immediately preceding
release work, as approximately two weeks. Both descriptions are true: seven
days of formal v0.9 merges occurred inside a longer period of continuous
project attention.

The report uses this evidence hierarchy:

1. exact Git commits, tags, and branch refs;
2. live GitHub issue, pull-request, workflow, release, and artifact state;
3. downloaded archive manifests and SHA-256 digests;
4. raw live-canary events, claims, ledgers, provider observations, PR receipts,
   and qualifier output;
5. repository tests and generated reports;
6. agent narrative only when corroborated by one of the above.

The following are deliberately not treated as completion evidence:

- an issue count;
- a closed issue;
- a source build;
- a unit or fixture test;
- a green pull request by itself;
- a green integration run by itself;
- a successful release-candidate workflow;
- an archive existing;
- a capability matrix claiming an implementation exists;
- an agent saying a stage is done.

Private repository names, local absolute paths, account identifiers, installation
identifiers, credentials, signed URLs, and provider session material are
intentionally omitted. Their hashes and local locations are not needed to
understand the project decision.

## 4. What v0.9.0 Was Intended to Be

### 4.1 Product objective

The owner did not ask for a larger collection of agent abstractions. The
practical objective was to turn already-paid provider capacity into reliable,
useful software delivery.

One human goal should have caused LoopCoder to:

- inspect the real providers and paid accounts available on the current
  machine;
- observe current model availability, model identity, depth/effort support, and
  remaining quota without exposing credentials;
- classify the goal into useful work with explicit requirements;
- build a bounded dependency graph;
- route each child to the best eligible provider/model/depth;
- reserve capacity without overcommitting it;
- perform useful work in isolated worktrees;
- retry only when the failure class allowed it;
- preserve exact identity across interruption and restart;
- integrate results without duplicate work;
- use an independent verifier;
- open a pull request with required checks;
- stop at a human decision gate; and
- explain, after the fact, exactly what route was chosen, why, what capacity was
  consumed, and what evidence proves the result.

The product was supposed to make multi-provider orchestration operationally
boring. It was not supposed to make the owner supervise a long sequence of
internal contracts and release candidates.

### 4.2 Final acceptance contract

The final contract was intentionally stricter than "the code seems to work."
It required exact binding across five layers:

| Layer | Required proof |
| --- | --- |
| Source | Exact `pre-prod` commit with same-SHA required checks |
| Integration | Exact merge-SHA `integration-verify` and `integration-canary` in one run |
| Artifact | Downloaded archive, manifest, binary identity, SBOM, and SHA-256 digest |
| Live behavior | Fresh private consumer run using real providers and a forced restart |
| Qualification | Raw evidence accepted; all required metrics `pass`; `not_run=0` |

This contract was correct in spirit. The failure was that it became fully
executable only after a very large implementation surface had already merged,
so it functioned as a late defect discovery engine instead of an early design
constraint.

### 4.3 Explicit non-goals

The approved v0.9 direction also excluded:

- LoopCoder using its own unfinished product to develop itself;
- provider-native development subagents replacing LoopCoder's own authority;
- autonomous production merges;
- fabricated inventory or default provider assumptions;
- fixture evidence substituting for real provider/account evidence;
- public release without an explicit owner GO.

Those exclusions should remain in force if the project is ever reconsidered.

## 5. Starting Point

The public baseline at the start of this cycle was `v0.8.1`, published on
2026-07-19 for native Darwin arm64.

v0.8.1 had connected several previously incomplete paths:

- worker route authority;
- verifier independence;
- DeliveryRun claim-dispatch;
- nested permission-safe routing;
- typed provider fallback;
- provider-free waits;
- host progress reporting;
- installer path handling; and
- release evidence harnesses.

The v0.9 effort was not a small increment over those paths. It attempted to
replace or consolidate major parts of:

- machine and project state ownership;
- lifecycle writers;
- provider discovery;
- model catalogs;
- quota observations;
- task classification;
- route eligibility and scoring;
- capacity reservations;
- workflow graph execution;
- cross-role materialization;
- integration;
- interruption and recovery;
- reporting;
- migrations;
- release packaging; and
- exact-artifact qualification.

That breadth is important when interpreting the later volume. The project
looked like a sequence of small PRs, but the product risk was a single large,
coupled system transition.

## 7. What Happened

### 7.1 2026-07-20: roadmap bootstrap and Gate A

The cycle began cautiously:

- [PR #1064](https://github.com/jasonhnd/loopcoder/pull/1064) defined a gated
  v0.9 architecture roadmap.
- The work was initially roadmap-only.
- A versioned v0.8.1 binary, isolated home, and isolated repository were used
  to avoid accidental self-development.
- Early Gate A work exposed that the existing dispatch path did not provide the
  route-decision authority required for the new program.

This was a reasonable start. The first warning was already present, however:
the desired product depended on replacing foundational authority before the
later provider and workflow layers could be trusted.

### 7.2 2026-07-21: reframe as ordinary development

The project was explicitly reframed away from self-bootstrap:

- [PR #1090](https://github.com/jasonhnd/loopcoder/pull/1090) described ordinary
  human-reviewable development.
- A catalog of 109 issues was published.
- Work was split into isolated issue/worktree/PR units.
- Four required CI classes - verify, test, race, and security - were used as
  merge gates.

This improved change isolation, but it also created a dangerous appearance of
control. A large system could now be merged as many small, individually green
transactions even though the final cross-component consumer path was not yet
available.

Foundation, storage, events, policy, runtime, UI visibility, direct-run,
provider, quota, routing, workflow, migration, packaging, and qualification
pieces began landing in rapid succession.

### 7.3 2026-07-21 through 2026-07-22: implementation burst

Across these two dates, 161 PRs merged.

The work included genuine implementation of:

- global and project authority stores;
- append-only events and projections;
- route and claim records;
- provider descriptor and observation interfaces;
- model and quota normalization;
- task capability classes;
- hard eligibility and fallback;
- WorkGraph definitions and scheduling;
- isolated child attempts;
- workflow cancellation and compaction;
- migration and compatibility tools;
- support and release evidence surfaces.

The problem was not that these PRs were empty. The problem was that their
individual tests could not establish the behavior of the whole product. The
project accumulated implementation claims much faster than it accumulated
live, exact-artifact evidence.

### 7.4 2026-07-22: first product-level correction

A product audit found foundational mismatches between the intended product and
the production path. Among them:

- production auto-route could use a fake or default inventory;
- real classified task requirements were not consistently consumed by `run`;
- provider model catalogs and depth support were not bound to fresh
  provider/account observations;
- quota reservation and reconciliation were incomplete;
- recovery identity and evidence were not yet exact enough for fail-closed
  qualification;
- qualification could accept derived summaries without fully validating raw
  events, claims, and ledgers.

The project then added a "core resource orchestration" correction program,
tracked through issues
[#1334](https://github.com/jasonhnd/loopcoder/issues/1334) through
[#1343](https://github.com/jasonhnd/loopcoder/issues/1343).

The correction work added or strengthened:

- fail-closed production inventory;
- fresh capacity snapshots;
- account-bound model/depth observations;
- real task classification;
- reservation ledgers;
- automatic goal decomposition;
- transparent child records;
- exact-artifact product metrics.

This was valuable work, but it was also a decisive signal that the initial
implementation program had merged before the central product path was proven.
At that point the project should have paused to rebuild a narrow vertical
acceptance slice. Instead it continued through another long sequence of fixes.

### 7.5 2026-07-22 through 2026-07-24: canary-driven defect discovery

Successive live and packaged canaries exposed defects in:

- quota and account observation;
- provider PTY behavior;
- permission/depth invocation;
- worktree ownership;
- child capacity attribution;
- qualifier arithmetic;
- forced interruption and restart;
- PR evidence;
- event and ledger identity;
- integration cleanup;
- unavailable-route handling;
- account association;
- exact model identity.

The tests were doing useful work: they found real production defects. But the
process pattern was inefficient:

1. build a candidate;
2. start a live canary;
3. discover the next defect;
4. create another issue and PR;
5. merge;
6. rerun exact-SHA integration;
7. build another candidate;
8. repeat.

Because every fix changed the exact SHA, no old archive could become the final
accepted archive. Candidate creation became part of debugging rather than a
final validation step.

### 7.6 2026-07-24 through 2026-07-25: provider truth was still moving

Provider observation proved more difficult than the static adapter contracts
suggested.

One concrete example was Claude usage. On the development host, the installed
CodexBar successfully returned fresh Claude machine JSON with:

```text
codexbar --provider claude --format json
```

LoopCoder's generic production bridge instead invoked a nonexistent command
shape:

```text
codexbar quota --schema codexbar.quota_bridge.v1 ...
```

That command failed as unknown, and LoopCoder's shorter timeout could also
expire before the real CodexBar result returned. The direct Claude PTY path had
another problem: a one-shot input strategy could stall at a workspace-trust
prompt even when authentication itself was valid.

[PR #1415](https://github.com/jasonhnd/loopcoder/pull/1415) and
[PR #1416](https://github.com/jasonhnd/loopcoder/pull/1416) corrected real
CodexBar usage and credential-safe account reporting. This work was effective.
It also demonstrated why a declared adapter catalog was not sufficient:
provider tools, authentication surfaces, account identity, prompts, and output
formats had to be observed on the actual machine.

After quota observation worked, Claude's model catalog was still only
adapter-declared. The next work added a verified subset based on bounded,
same-account real invocations. More changes followed for:

- account-bound catalog evidence;
- environment and invocation isolation;
- receipt aliasing;
- exact Opus usage;
- interruption permissions;
- log evidence;
- restart PR and cache behavior;
- genuine unavailable-model evidence;
- alternate model identity.

Each fix was defensible in isolation. Together they showed that the provider
truth model had not stabilized before release-candidate testing began.

### 7.7 2026-07-26: the last acceptance sequence

The final day concentrated on exact restart and evidence identity:

- resume route identity;
- ignored receipt handling;
- generation domains;
- verifier reuse;
- UI measurement;
- verifier findings;
- test validation contracts;
- Go module-cache cleanup;
- exact forced-restart evidence.

The last merge was
[PR #1449](https://github.com/jasonhnd/loopcoder/pull/1449), "Fix exact
forced-restart acceptance evidence," producing stopped `pre-prod` SHA
`30cabdaf77d749c8305349f7f6a87189014b8af8`.

The exact merge-SHA integration workflow
[run 30192984058](https://github.com/jasonhnd/loopcoder/actions/runs/30192984058)
completed successfully.

The draft RC workflow
[run 30193014249](https://github.com/jasonhnd/loopcoder/actions/runs/30193014249)
then built `0.9.0-rc.61`.

Before the `rc.61` live consumer canary and qualifier started, the owner stopped
development. The continuation agent was closed and the monitoring automation
was paused. No v0.9 process was left running.

### 8.3 What may be retained as useful engineering

The following are likely valuable assets, subject to a fresh audit:

- fail-closed authority concepts;
- typed provider observation and provenance;
- explicit task requirement classification;
- route decision records;
- bounded WorkGraph and child contracts;
- interruption and generation identity work;
- independent verifier evidence;
- archive/manifest/digest binding;
- raw-evidence qualification that rejects contradictions;
- credential-safe reporting;
- the large set of negative canary findings.

They should be treated as an experimental branch of the product, not as a
supported platform. No component should be promoted into a public release
merely because its focused tests pass. Its dependencies and production call
sites must be re-audited first.

## 10. Why the Project Did Not Finish

### 10.1 The target was too broad for one release cycle

v0.9 simultaneously changed state authority, providers, catalogs, quota,
routing, graph execution, recovery, integration, reporting, migration, and
release qualification.

Each area has its own failure modes. Their cross-product is much larger than the
sum of the issue count. A route can be correct while its provider observation
is stale; a child can complete while its capacity ledger is wrong; a restart
can visibly succeed while its attempt identity is ambiguous; a PR can be green
while its evidence envelope cannot prove how it was produced.

The program should have been decomposed into one production vertical slice at a
time, each with a frozen consumer acceptance contract.

### 10.2 Architecture contracts landed before production reachability

Many early PRs established types, schemas, fixtures, and adapters. Later audits
found that production entry points still used fake/default inventory or failed
to consume real task requirements.

This is a classic reachability failure:

- a correct component existed;
- tests proved the component;
- documentation described the component;
- the user-facing command did not necessarily call it with real data.

The project repeatedly treated component existence as progress toward product
completion without immediately proving the production call graph.

### 10.3 The acceptance harness matured too late

The strongest qualifier behavior appeared near the end. By then it was
validating a large system and discovering foundational identity and arithmetic
problems.

The exact artifact contract should have been frozen before most implementation:

- canonical raw event schema;
- claim and attempt identity;
- capacity arithmetic;
- unavailable-route successor identity;
- restart generation identity;
- PR/check binding;
- explicit metric extraction.

Instead, runtime and qualifier evolved together. A runtime fix could require a
qualifier fix; a qualifier fix could reveal that earlier runtime evidence was
insufficient. This prevented a stable definition of "done" from operating as a
development boundary.

### 10.4 Real provider integrations invalidated static assumptions

Provider behavior was not a stable library API:

- installed CLI versions differed;
- model names and availability changed;
- accounts had different entitlements;
- quota windows came from different confidence levels;
- OAuth and workspace-trust prompts affected invocation;
- trusted third-party tools had their own command and latency behavior;
- some official endpoints failed or did not expose the required information.

The project initially encoded assumptions that only failed on the real machine.
The Claude/CodexBar command mismatch is the clearest example.

Fresh provider observation was a core product requirement, not an optional
adapter enhancement. It should have been proven in isolation before graph,
quota, and routing logic depended on it.

### 10.5 PR and CI gates measured local correctness, not convergence

The four-green policy improved individual PR safety. It did not answer:

- Does the exact merged product complete one real consumer goal?
- Is every required metric currently executable?
- Is the number of unresolved acceptance classes decreasing?
- Did this change invalidate prior product evidence?
- Is the project closer to an accepted artifact than it was one day ago?

At 73 and 88 merges per day, the process could not plausibly provide ordinary
human comprehension of the combined behavior. "One issue, one worktree, one
PR" protected repository transactions, but it did not protect the product from
integration debt.

### 10.6 RC creation was used as a debugging loop

A release candidate should be built after the product and acceptance harness
are frozen. Here, candidates were often built to find the next problem.

That had three costs:

1. each source fix invalidated the previous archive;
2. archive version growth created a false sense of advancement;
3. repeated setup, download, refresh, canary, and cleanup consumed time without
   producing durable acceptance.

The process needed a rule: no new RC until all required qualifier metrics can
run against a locally packaged exact binary and all known product blockers are
closed on that same source SHA.

### 10.7 The project had no effective stop-loss mechanism

The monitoring instruction was optimized to keep work moving through routine
issue, PR, CI, merge, integration, RC, and canary boundaries. That prevented
minor stalls, but it also suppressed the most important project-management
question: should the cycle continue at all?

There was no enforced threshold such as:

- maximum elapsed days without one accepted vertical slice;
- maximum RCs without reduction in failed requirement classes;
- maximum newly discovered release blockers after a product NO-GO;
- maximum source churn after the first exact-artifact attempt;
- mandatory owner checkpoint after two failed live canaries.

Without those thresholds, "continue only the incomplete stage" became a local
instruction that perpetuated a globally non-convergent process.

### 10.8 Completion reporting did not protect the owner

The oversight process repeatedly communicated concrete local progress:

- a PR merged;
- four checks were green;
- exact integration passed;
- an archive was built;
- another defect was fixed;
- a real provider executed;
- a PR reached a human gate.

Those statements could be true while the only product-level statement remained
"still `NO_GO`."

The owner should have received a stable top line after every cycle:

```text
Accepted exact artifact: no
Required metrics passed: N / total
Required metrics not_run: N
New blocker classes discovered: N
Elapsed time since last product-level convergence: N
Recommendation: continue / pause / stop
```

That did not happen consistently. The process made activity legible, but not
the absence of convergence. It therefore failed to protect the owner's time and
trust.

## 11. Accountability

### 11.1 What the engineering process did well

It is important not to erase useful work:

- defects were usually recorded rather than hidden;
- exact SHAs and artifact digests were preserved;
- public release was never performed without owner authorization;
- the qualifier ultimately failed closed;
- the independent verifier found real consumer defects;
- real provider/account behavior replaced several fabricated assumptions;
- `rc.60` demonstrated substantial end-to-end behavior;
- credentials and account identity were increasingly redacted;
- the stop was honored without publishing `v0.9.0`.

### 11.2 What the engineering process did poorly

The process:

- accepted a scope too large for one release;
- merged contracts before proving production reachability;
- allowed extreme PR throughput to masquerade as controlled development;
- treated successful RC builds as stage progress;
- repeatedly repaired the canary rather than freezing its contract early;
- did not establish a convergence dashboard;
- did not create stop-loss checkpoints;
- continued after multiple strong signals that the architecture and evidence
  model were still unstable;
- required the owner to wait while internal correctness displaced the requested
  product outcome.

### 11.3 Oversight and automation failure

The principal oversight failure was persistence without sufficient
re-evaluation.

The agent and monitoring process were effective at finding the next incomplete
step and ineffective at deciding when the overall strategy had failed. They
continued across routine boundaries because each next action was individually
reasonable. That local rationality produced a poor global result.

The correct responsibility statement is:

> The owner gave a product objective and substantial operating authorization.
> The development and oversight process failed to convert that authorization
> into a bounded, convergent delivery program. It allowed scope, artifact
> iteration, and acceptance defects to consume too much time before presenting
> a stop recommendation. That failure belongs to the process, not to the owner.

Several moments should have triggered a formal pause.

### 12.1 After RC2

Correct response:

- freeze feature work;
- identify the smallest live vertical slice;
- freeze its raw evidence schema;
- refuse another RC until that slice passed.

Actual response:

- continued broad implementation and candidate iteration.

### 12.2 After the core orchestration audit

- reduce scope.

Actual response:

### 12.3 Around RC37

Real Claude quota worked, but the model catalog remained static and

Actual response:

### 12.5 After RC58 and RC59

RC58 blocked twice on ordinary generated-project correctness. RC59 blocked on

## 17. Lessons

### 17.1 Begin with one accepted vertical slice

Before publishing 109 issues, prove:

```text
one goal
-> one real inventory
-> two useful children
-> one provider execution
-> one interruption or failure
-> one PR
-> one exact evidence envelope
-> one qualifier pass
```

Only then expand provider count, graph complexity, migration, and release
surfaces.

### 17.2 Freeze acceptance before implementation breadth

Define raw events, claims, capacity arithmetic, restart identity, and metric
extraction first. A qualifier that changes with the runtime cannot provide a
stable finish line.

### 17.3 Prove production reachability, not component existence

Every new subsystem needs a user-command test that proves:

- the production entry point calls it;
- the data is real rather than default;
- stale or unavailable data fails closed;
- the resulting evidence is visible to the user.

### 17.4 Treat provider truth as perishable

Model catalogs, quota, prompts, accounts, and CLI output must be observed from
the current installation. Static adapter rows are hints, not authority.

### 17.5 Use PR gates and product gates for different purposes

PR gates answer "is this change locally safe to merge?" Product gates answer
"does one exact artifact deliver the user outcome?" Both are necessary.
Neither substitutes for the other.

### 17.6 Stop building RCs during active defect discovery

Use local packages or explicitly named integration snapshots while the product
is still changing. Reserve RC labels for frozen-source validation.

### 17.7 Measure convergence

Track at least:

- accepted requirements;
- invalid requirements;
- `not_run` requirements;
- new blocker classes;
- artifact-invalidating changes;
- days since last reduction in product-level failure classes.

Activity metrics such as commits, issues, PRs, and RC numbers must never lead
the status.

### 17.8 Install mandatory stop-loss rules

Recommended default:

- owner checkpoint after two failed live canaries;
- mandatory pause when a product audit finds a fake production dependency;
- no more than one new RC without a reduction in failed requirement classes;
- no more than three RCs after the first exact-artifact `NO_GO`;
- no continuation after five business days without one accepted vertical slice
  unless the owner explicitly renews the budget.

### 17.9 Separate diagnostic success from product success

A failed verifier that catches a red test is a diagnostic success. A qualifier
that rejects contradictory evidence is a diagnostic success. Neither means the
product succeeded.

### 17.10 Protect the owner from internal complexity

The owner should not need to interpret dozens of RCs or hundreds of PRs.
Reporting must lead with:

- usable product: yes/no;
- exact accepted artifact: yes/no;
- unmet user requirements;
- time and risk trend;
- continue/pause/stop recommendation.

## 18. Counterfactual Delivery Plan

## 20. Future Options

These are choices for a future owner review, not a recommendation to act now.

### Option A: archive indefinitely

Keep v0.8.1 as the last public line, preserve this report and the stopped ref,
and do no further work.

Advantages:

- no additional cost;
- no accidental release;
- preserves learning and code.

Risks:

- dependencies and provider integrations drift;
- resumption becomes more expensive over time.

### Option B: extract a small subset into a maintenance release

Audit selected independent improvements and port only those with a clear
v0.8.1 production benefit.

Advantages:

- recovers value from some engineering;
- avoids the full v0.9 architecture.

Risks:

- hidden coupling may be substantial;
- requires fresh testing and release authorization;
- must not be presented as v0.9 completion.

### Option C: restart with a narrower product

Design a new milestone around one vertical multi-provider path and a frozen
qualifier.

Advantages:

- strongest chance of convergence;
- lessons can directly shape scope.

Risks:

- much existing code may be discarded;
- still requires a new budget and owner commitment.

### Option D: resume the stopped branch

Continue from `30cabdaf...` and attempt final acceptance.

Advantages:

- preserves the largest amount of existing work.

Risks:

- highest integration and stale-assumption risk;
- RC61 was never live-tested;
- open blockers remain;
- provider catalogs and artifacts are perishable;
- prior history shows a strong tendency toward serial defect discovery.

Option D must not be the default merely because it appears closest to release.

## 22. Final Statement

v0.9.0 produced real code, real fixes, real provider runs, real negative
evidence, and a real human-gated pull request. It did not produce one exact
artifact that satisfied the owner's complete product contract.

The development process confused a high rate of local completion with global
convergence. It kept solving the next technically valid problem after the
project should have paused and reconsidered its delivery strategy. The result
was too much elapsed time, too much integration churn, and no supported v0.9
product.

The project is therefore stopped at
`30cabdaf77d749c8305349f7f6a87189014b8af8`.

`0.9.0-rc.61` is preserved only as an unaccepted internal snapshot.

`v0.8.1` remains the latest public release.

No v0.9 tag or release may be created without a new, explicit owner decision
and a fresh exact-artifact acceptance record.
