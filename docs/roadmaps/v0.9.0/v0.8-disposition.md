# v0.8.1 Implementation Disposition For v0.9.0

Status: detailed draft

This document prevents v0.9.0 from becoming another layer over v0.8.1. It maps
the current implementation to an explicit disposition before new work begins.
The map was prepared from `pre-prod` at
`8e236e7cadd38c1df1e341e95b86f46754cb1034`.

The map is planning evidence, not permission to delete code. Every removal needs
replacement parity, migration evidence, and its own accepted issue.

## Repository Shape

The current repository contains more than 460 Go files, more than 80 documents,
and more than 50 specifications. Several packages are already product-scale:

| Package | Approximate Go lines | Observation |
| --- | ---: | --- |
| `internal/cli` | 32,000 | One command package imports nearly every subsystem and exposes a large advanced command inventory. |
| `internal/orchestration` | 24,000 | Tick, trigger, promotion, risk gates, wait behavior, and compatibility decisions share one ownership area. |
| `internal/routing` | 21,000 | Rich v0.8 policy, decision, fallback, council, and persistence behavior already exists. |
| `internal/storage` | 20,000 | Schema version 31 contains projects, runs, reports, delivery, provider, quota, progress, routing, federation, nested, and handoff tables. |
| `internal/providerinventory` | 17,000 | Discovery, auth, model, quota, refresh, and reconciliation mechanics are broad and partly overlapping. |
| `internal/progress` | 9,000 | Receipts, outbox, delivery attempts, acknowledgements, replay cursors, sinks, and followers already exist. |
| `internal/worker` | 6,500 | Worktree, provider invocation, report, commit, push, and PR stages remain tightly coupled. |
| `internal/agent` | 6,300 | Codex, Claude, Antigravity, Gemini, and Grok invocation adapters contain useful bounded execution mechanics. |
| `internal/delivery` | 5,900 | DeliveryRun, task, attempt, decision, claim, continue, and persistence behavior overlaps the intended compact model. |
| `internal/supervisedexec` | 4,300 | Process groups, liveness, hard caps, output handling, and macOS guardian behavior are valuable runtime foundations. |
| `internal/store` | 2,100 | New R1.3 compact-store foundation is isolated but currently carries unnecessary Windows ACL implementation. |

The size is not itself a defect. The risk is that v0.9 might build a second
inventory, router, scheduler, report system, or process supervisor without first
selecting one writer and one public path.

## Disposition Vocabulary

| Disposition | Meaning |
| --- | --- |
| Keep | Preserve package and behavior after focused conformance evidence. |
| Reuse behind facade | Preserve low-level mechanics, but route the new product through a smaller v0.9 interface. |
| Consolidate | Choose one v0.9 owner and migrate useful behavior out of several current packages. |
| Compatibility-only | Keep old command/reader for one release; it never writes new-path state. |
| Remove after parity | Delete only after replacement, migration, and release evidence pass. |
| Reject | Do not reproduce this behavior on the v0.9 path. |

### Store decision

Do not extend schema version 31 for the new path. Do not let `internal/store` and
`internal/storage` both write one project. The v0.9 binary opens old storage only
through an explicit read-only exporter. New machine and project stores have
separate files, independent schema ledgers, and explicit evidence links.

### Visibility decision

Persisting a receipt, writing stderr, or leaving a relay record is not proof the
operator saw progress. v0.9 stores one event, projects current status, streams
from one cursor, and records only the highest final-mile stage each UI client
can prove: `persisted`, `streamed`, `accepted`, `rendered`, or `seen`.

The terminal client is the reference. The local loopback HTTP/SSE and JSON
bridge is the generic integration surface. Paseo is the first external
conformance client, not a runtime dependency or privileged route. Codex, Claude,
editors, desktop applications, and future clients must pass the same black-box
contract. A UI without a documented inbound presentation surface degrades
honestly to terminal or another declared client; it is not listed as in-session
capable.

### Provider decision

Provider code is migrated by method family, not rewritten as one large issue.
Each official provider has two small conformance issues: discovery/catalog/
invocation, then quota. A shared fake CLI/API harness merges first. Credentials
remain in the provider's supported auth system; snapshot payloads contain no
secret material.

### Route decision

An explicit owner pin is immutable for that attempt. Recovery cannot reinterpret
an old pin through current defaults. Automatic routing filters hard eligibility,
then ranks fresh evidence. Quota burn urgency applies only after capability and
risk requirements pass. A language model does not select the company that will
run the task.

### Runtime decision

Do not implement a second provider launcher. The v0.9 Runtime facade wraps
existing agent/supervisedexec mechanics, adds process-tree CPU/RSS/descendant
accounting, and stores one Attempt lifecycle. OS liveness, semantic progress,
UI delivery, and provider-native status remain distinct observations.

### Delivery decision

`loopcoder run` is an explicit stage machine. Worker execution, focused checks,
commit, push, PR, CI wait, verifier, and human gate each persist completion
evidence separately. A push timeout reconciles the remote branch and resumes
push/PR delivery; it never reruns the worker. Remote CI owns full repository and
race/security evidence.

### Workflow decision

The one-node graph is the default. Explicit workflows arrive after direct-run
acceptance. They use stable WorkItems, blocking edges, deterministic ready set,
atomic claim/close, bounded waves, one writer per worktree, and ordered
integration. Provider-native sub-agents remain children of one Attempt and do
not become WorkItems unless LoopCoder explicitly materializes cross-provider
work.

## CLI And Documentation

The v0.8 README lists dozens of commands before a user can complete one normal
task. The v0.9 root help and README must lead with:

```text
loopcoder run
loopcoder status
loopcoder events
loopcoder cancel
loopcoder doctor
loopcoder providers
loopcoder route explain
```

Advanced v0.8 commands remain under an explicit compatibility group for one
release. Command existence is not a support claim. The capability matrix names
tested product paths, provider evidence, host final-mile stage, and unsupported
combinations.

## Deletion Order

Deletion is delayed until the replacement has exact evidence:

1. new machine/project stores and importer pass before old storage becomes
   read-only;
2. event/status/host canaries pass before relay/outbox/report lifecycle writers
   are removed;
3. direct-run canaries pass before default tick/dispatch-wave/trigger paths are
   hidden;
4. provider conformance passes before old inventory/routing writers are removed;
5. bounded-workflow canary passes before nested/federation state is removed;
6. cross-Mac GitHub rehydration passes before state branches and leases are
   removed; and
7. exact-artifact migration smoke passes before compatibility code is deleted
   from the release branch.

No deletion issue may combine replacement implementation and old-system
removal. That separation preserves rollback and makes regressions attributable.
