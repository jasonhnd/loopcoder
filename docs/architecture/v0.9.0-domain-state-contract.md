# v0.9.0 Domain/state Contract

Status: draft
Roadmap ref: Phase R1 / R1.1 Domain/state contract
Issue: #1082
Stable ID: R1.1 Domain/state contract

## Purpose

This document defines the v0.9.0 domain and state contract for the Go-native
core. It names the core nouns, their authority boundaries, legal state
transitions, idempotency rules, replay behavior, and source-of-truth split
between GitHub, local LoopCoder state, and provider process evidence.

This is documentation only. It does not implement storage, define schema DDL,
name Go packages, change CLI behavior, activate later R1 slices, or change
provider adapters, dispatch, verification, release, or packaging behavior.

## Core Nouns

| Noun | Definition | Owner and authority |
| --- | --- | --- |
| `Project` | A normalized GitHub repository identity plus local aliases LoopCoder has observed for that repository. | GitHub owns repository identity, visibility, branches, commits, issues, PRs, reviews, and checks. LoopCoder owns local path aliases, local project projections, and machine-local state under its own home. Local aliases never redefine the GitHub repository. |
| `WorkItem` | A durable unit of requested work. The default WorkItem is one GitHub issue; explicit bounded workflow mode may later materialize additional visible nodes. | GitHub owns requested work text, issue lifecycle, labels, comments, PR linkage, and collaborative completion evidence. LoopCoder owns local readiness, claim, job, attempt, event, and status projections for the current machine. Provider prose cannot create or complete a WorkItem. |
| `Dependency` | A directed blocker relationship from one WorkItem to another. A blocked WorkItem cannot be claimed until its dependencies are satisfied or explicitly removed by the authority that owns the dependency. | GitHub owns collaboration-visible dependency markers. LoopCoder owns local dependency projections, ready-set computation, and conflict classification. Local projections must be refreshed from GitHub before cross-session decisions. |
| `Job` | One local execution plan admitted for a WorkItem. A Job owns the local route, resource ceiling, worktree boundary, delivery objective, and gate sequence for that execution. | LoopCoder local state owns Job lifecycle and claim exclusivity. GitHub delivery evidence and configured gates decide whether the Job's output can satisfy the WorkItem. |
| `Attempt` | One bounded execution of a Job by one selected Provider/Model route and one owned process tree. | LoopCoder owns Attempt lifecycle, timeout, stop, replay, and process ownership records. Provider process truth owns observed process facts such as launched PID, native status, output, exit code, and supported hooks. Attempt success requires LoopCoder-observed evidence, not provider prose alone. |
| `Provider` | An external execution system, normally a locally installed coding agent or provider CLI, used for Worker or Verifier execution. | The provider system owns authentication, account state, credentials, native availability, and any authoritative quota it exposes. LoopCoder owns adapter policy, non-secret readiness observations, admission decisions, and bounded usage records. |
| `Model` | A provider-scoped execution choice selected for an Attempt. | The provider owns model availability, model-side limits, and model deprecation. LoopCoder owns the selected route record, freshness/confidence of model inventory observations, and the rule that one Attempt is pinned to one selected Provider/Model route. |
| `Gate` | A named decision boundary that can allow, block, fail, or route work to human review. Gates include local policy, resource ceilings, delivery evidence, remote CI, independent verification, and human merge/release decisions. | Each Gate is authoritative only for its own surface. LoopCoder records the verdict and evidence pointer, but it must not let a local or provider gate override GitHub, remote CI, independent verifier, or human authority. |
| `Event` | An immutable observed fact accepted into the local event stream for a Project, WorkItem, Job, Attempt, Provider, Model, or Gate. | LoopCoder local state owns event identity, ordering, idempotency, and replay. The event source determines factual authority: GitHub events cite GitHub evidence, provider events cite provider process evidence, and local events cite LoopCoder-controlled observations. |

## Authority Surfaces

| Surface | Authoritative for | Not authoritative for |
| --- | --- | --- |
| GitHub | Requested work, issue/PR state, branch and commit identity, reviews, hosted checks, labels, dependency markers visible to collaborators, merge and release collaboration state. | Current local process liveness, local attempt ownership, provider account health, local readiness cache, or machine-local event replay. |
| Local LoopCoder state | Project aliases, WorkItem projections, Dependency projections, Job claims, Attempt lifecycle, local events, route decisions, local resource ceilings, local status projections, idempotency records, replay cursors. | Delivery completion without GitHub evidence, provider credentials, authoritative provider quota, or production merge approval. |
| Provider process truth | Whether a provider process launched, remained live, emitted output, reported native status, exited, timed out, or exposed a supported structured hook result. | WorkItem completion, GitHub delivery truth, merge eligibility, retry authority, or credential custody. |
| Provider account system | Authentication state, credentials, provider-owned account status, and authoritative quota when exposed by the provider. | LoopCoder readiness policy, Job admission, WorkItem completion, or local event ordering. |
| Human/operator gate | Explicit approvals, merge/release decisions, ambiguous side-effect resolution, and overrides that the accepted process requires to be human-gated. | Silent background mutation or retroactive rewriting of immutable event history. |

When surfaces disagree, LoopCoder must preserve the disagreement as evidence and
route to `needs_human` or a blocked state. It must not silently prefer a weaker
surface over the authority that owns the disputed fact.

## WorkItem States

WorkItem state is a local projection over GitHub truth, dependencies, Jobs,
Attempts, and Gates. It is not a replacement for the GitHub issue.

| State | Meaning |
| --- | --- |
| `observed` | GitHub or an approved workflow plan names the WorkItem, but LoopCoder has not yet classified readiness. |
| `blocked` | One or more Dependencies, gates, or human decisions prevent claim. |
| `ready` | Dependencies are satisfied and local policy may admit a Job. |
| `claimed` | One local Job holds the active claim for the WorkItem. |
| `active` | The claimed Job has a running, waiting, stopping, or recovering Attempt. |
| `in_review` | The Job produced reviewable delivery evidence and one or more delivery, CI, verifier, or human gates remain open. |
| `needs_human` | Authority is ambiguous or an accepted process requires operator input before continuing. |
| `done` | The owning GitHub and gate evidence prove the WorkItem is satisfied. |
| `failed` | The WorkItem cannot continue within the accepted scope and retry budget. |
| `cancelled` | The owning authority intentionally stopped the WorkItem before completion. |
| `superseded` | A newer WorkItem or explicit owner decision replaces this WorkItem. |

Legal WorkItem transitions are:

| From | To |
| --- | --- |
| `observed` | `blocked`, `ready`, `cancelled`, `superseded` |
| `blocked` | `ready`, `needs_human`, `cancelled`, `superseded` |
| `ready` | `claimed`, `blocked`, `needs_human`, `cancelled`, `superseded` |
| `claimed` | `active`, `ready`, `needs_human`, `cancelled`, `superseded` |
| `active` | `in_review`, `ready`, `needs_human`, `failed`, `cancelled`, `superseded` |
| `in_review` | `done`, `ready`, `needs_human`, `failed`, `cancelled`, `superseded` |
| `needs_human` | `blocked`, `ready`, `cancelled`, `superseded` |
| `done`, `failed`, `cancelled`, `superseded` | No state-changing transition; exact replay is a no-op. |

Illegal WorkItem transitions are forbidden. In particular:

- A WorkItem must not move to `done` from provider prose, provider exit code, or
  local claim state alone.
- A WorkItem must not move from any terminal state back to active work without a
  new WorkItem or an explicit supersession path.
- A WorkItem must not be claimed while it is blocked, terminal, or already
  actively claimed by another local owner.
- A WorkItem must not skip from `observed` to `active`; a local claim and Job
  must exist first.

## Job States

A Job represents local execution ownership for one WorkItem. Job state answers
"what LoopCoder is doing locally for this WorkItem now."

| State | Meaning |
| --- | --- |
| `queued` | LoopCoder admitted the Job but has not claimed execution resources. |
| `claimed` | The Job holds local exclusive ownership for execution. |
| `running` | One Attempt is executing provider work or deterministic local delivery work. |
| `waiting` | The Job is waiting on a deterministic external condition such as CI, human approval, quota reset, retry deadline, or host delivery. |
| `blocked` | A policy, resource, dependency, or authority conflict prevents progress. |
| `verifying` | Delivery evidence exists and verification or gate checks are evaluating it. |
| `stopping` | LoopCoder is trying to stop the owned process tree or close local resources. |
| `succeeded` | The Job satisfied its local objective and all required owning gates for the Job passed. |
| `failed` | The Job exhausted scope or retry budget, or a required gate failed. |
| `cancelled` | The Job was intentionally stopped before completion. |
| `timed_out` | The Job exceeded an explicit deadline. |
| `needs_human` | The Job cannot choose the next action safely without operator input. |

Legal Job transitions are:

| From | To |
| --- | --- |
| `queued` | `claimed`, `blocked`, `cancelled`, `needs_human` |
| `claimed` | `running`, `blocked`, `cancelled`, `needs_human` |
| `running` | `waiting`, `verifying`, `stopping`, `succeeded`, `failed`, `timed_out`, `needs_human` |
| `waiting` | `running`, `verifying`, `stopping`, `succeeded`, `failed`, `timed_out`, `needs_human` |
| `blocked` | `queued`, `claimed`, `cancelled`, `needs_human` |
| `verifying` | `waiting`, `succeeded`, `failed`, `needs_human` |
| `stopping` | `cancelled`, `failed`, `timed_out`, `needs_human` |
| `needs_human` | `queued`, `blocked`, `cancelled` |
| `succeeded`, `failed`, `cancelled`, `timed_out` | No state-changing transition; exact replay is a no-op. |

Illegal Job transitions are forbidden. A Job must not:

- run before it has exclusive local claim ownership;
- succeed while its required WorkItem, delivery, CI, verifier, or human Gate is
  still unresolved;
- run two active Attempts at the same time unless a later accepted bounded
  workflow policy explicitly creates separate visible child WorkItems; or
- change a terminal outcome by replaying a different completion payload.

## Attempt States

An Attempt represents one bounded Provider/Model/process execution for a Job.
Attempt state answers "what happened to this execution."

| State | Meaning |
| --- | --- |
| `created` | The Attempt identity and selected route exist, but no process has launched. |
| `starting` | LoopCoder is preparing or launching the provider process. |
| `running` | The provider process or owned deterministic delivery stage is active. |
| `waiting` | The Attempt is waiting on a bounded deterministic condition it owns. |
| `stopping` | LoopCoder has requested stop and is joining or harvesting owned process evidence. |
| `succeeded` | The Attempt produced LoopCoder-observed evidence satisfying its bounded objective. |
| `failed` | The Attempt ended with a classified failure. |
| `cancelled` | The Attempt was intentionally stopped. |
| `timed_out` | The Attempt exceeded its deadline. |
| `needs_human` | The Attempt ended in ambiguity, unsafe side effects, or unclassified authority conflict. |

Legal Attempt transitions are:

| From | To |
| --- | --- |
| `created` | `starting`, `cancelled` |
| `starting` | `running`, `failed`, `timed_out`, `needs_human` |
| `running` | `waiting`, `stopping`, `succeeded`, `failed`, `timed_out`, `needs_human` |
| `waiting` | `running`, `stopping`, `succeeded`, `failed`, `timed_out`, `needs_human` |
| `stopping` | `cancelled`, `failed`, `timed_out`, `needs_human` |
| `succeeded`, `failed`, `cancelled`, `timed_out`, `needs_human` | No state-changing transition; exact replay is a no-op. |

Illegal Attempt transitions are forbidden. An Attempt must not:

- start without a Job claim and selected Provider/Model route;
- move to `succeeded` from a provider self-report that lacks local observable
  evidence;
- mutate its Provider/Model route after launch;
- be reused for a retry after terminal failure; retries create a new Attempt
  under the same Job or a successor Job, according to the accepted retry policy;
  or
- hide an ambiguous process, partial side effect, or missing terminal evidence
  behind `succeeded`.

## Idempotency And Replay

Every state-changing operation must carry an idempotency key. The key identifies
the intended operation, target Project, target entity, owner, and normalized
payload. The exact key encoding is left to later implementation, but the
semantic fields are part of this contract.

| Operation class | Required key scope | Replay behavior |
| --- | --- | --- |
| Create Project or WorkItem projection | Operation name, GitHub repository identity, external issue or approved workflow-node identity, and normalized source payload. | Replaying the same key with the same payload returns the original identity and emits no duplicate entity. Same key with different payload is a conflict. A different key for the same external identity must adopt the existing entity or route to conflict; it must not create a duplicate WorkItem. |
| Create Dependency | Operation name, Project, blocked WorkItem, blocking WorkItem, dependency source, and normalized source payload. | Replaying the same dependency is a no-op. Conflicting direction, source, or removal state must be recorded as a conflict or human decision, not silently rewritten. |
| Create Job | Operation name, Project, WorkItem, run or execution owner, delivery objective, and normalized admission payload. | Replaying the same key returns the existing Job. A second non-terminal Job for the same WorkItem is rejected unless the prior Job is terminal or explicitly superseded. |
| Claim WorkItem or Job | Operation name, Project, WorkItem or Job, claimant identity, lease or ownership epoch, and expected current state. | Replaying the same live claim by the same claimant returns the existing claim. A claim against a stale expected state fails closed. A competing active claimant receives a conflict and must not steal ownership without an explicit release, expiry, or human decision event. |
| Create Attempt | Operation name, Project, Job, attempt ordinal or stable attempt identity, Provider, Model, work boundary, and normalized route payload. | Replaying the same key returns the existing Attempt. A retry after a terminal Attempt uses a new Attempt identity. A different Provider/Model for the same Attempt identity is a conflict. |
| Complete WorkItem, Job, or Attempt | Operation name, target entity, terminal state, source authority, evidence pointer, and normalized completion payload. | Replaying the same completion is a no-op. Same key with different terminal state or evidence is a conflict. A terminal entity does not change terminal state through replay; corrections require a separately authorized supersession or successor entity. |
| Append Event | Operation name, Project, event source, event subject identity, source occurrence identity when available, and normalized event payload. | Replaying the same event returns the original sequence. Duplicate transport delivery is tolerated. Same key with different payload is a conflict and must not allocate a second sequence for the disputed fact. |

Replay must never repeat provider execution, GitHub mutation, PR creation,
merge, release, verifier execution, or report delivery side effects merely
because a host disconnected, a watcher restarted, or a command was retried.
Replay reads existing evidence first and continues from the next incomplete
legal transition.

## Event Rules

Events are immutable facts, not commands. They must preserve enough identity to
rebuild current projections without trusting the current host conversation.

Every accepted Event must identify:

- Project;
- subject noun and subject identity;
- source surface, such as GitHub, local LoopCoder, provider process, provider
  account, verifier, gate, host bridge, or human/operator;
- occurrence time when known and accepted write time;
- idempotency key;
- ordered local sequence;
- prior and next state when the Event is a state transition; and
- bounded evidence pointer or redacted summary.

Events must not contain provider credentials, raw secret values, unbounded
provider transcripts, or repository-visible copies of local-only report
payloads. Redacted summaries and local evidence pointers are allowed when a
later reader can still classify the state honestly.

Current status is a projection derived from Events plus fresh authority reads
where required. A projection may be compact and replaceable, but it must not
invent a state transition that is absent from the event stream.

## Ownership Boundaries

The Work Graph owns WorkItem, Dependency, readiness, and claim semantics. Store
and Events owns idempotent acceptance, ordering, event replay, and projections.
Runtime and Supervisor own process launch, liveness, stopping, timeout, and
process evidence. Provider Plane owns provider and model inventory observations.
Router owns route eligibility and deterministic selection decisions. Delivery
owns worktree, GitHub PR/check observation, verifier, and merge/release gate
evidence. Host Bridge owns event following, cursor acknowledgement, and
final-mile report delivery evidence.

Those destinations are named only as architectural ownership boundaries. This
document does not require a package layout, database schema, CLI surface, file
format, or migration mechanism.

## Scope Boundaries

This contract is the R1.1 input for later R1 slices. It does not:

- implement SQLite schema, migrations, Work Graph runtime, event APIs, or CLI
  commands;
- change provider adapters, provider model selection, dispatch, loopreview,
  release, or packaging behavior;
- activate R1.2 or later roadmap slices;
- introduce repository-local state or old-engine writes; or
- open or publish additional issues.

Future implementation PRs must cite the accepted contract they implement and
stay inside their own roadmap slice.
