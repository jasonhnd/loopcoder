# LoopCoder v0.9.0 UI Report Protocol

Status: development-ready normative v0.9.0 contract; owner acceptance required

## Purpose

LoopCoder is a headless local execution core. Terminal output, Paseo, Codex,
Claude Code, browser-based tools, desktop applications, and future operator
interfaces are clients of the same public reporting and control protocol. No UI
is lifecycle authority, and no UI-specific package may become a dependency of
the event store, runtime, provider plane, router, or workflow scheduler.

The product requirement is end-to-end receipt, not merely report generation.
Persisting an event, writing stderr, creating an outbox row, or detecting a host
does not prove that an operator received a report. A UI integration may claim
only the highest delivery stage for which it has concrete acknowledgement.

## Architectural Boundary

The protocol has four layers:

1. **Authoritative event:** the append-only project event committed by the
   LoopCoder core.
2. **Report projection:** a bounded, redacted, versioned operator-facing view of
   one or more accepted events.
3. **Transport:** a replaceable mechanism that carries reports and actions.
4. **UI adapter:** a client that renders reports, acknowledges delivery, and
   submits explicitly authorized operator actions.

The protocol is named `loopcoder.ui.v1`. Its JSON schemas and golden transcripts
are public compatibility artifacts. A new UI that implements those artifacts
must be able to integrate without editing LoopCoder lifecycle code.

## Required Report Kinds

Every non-dry-run execution emits the following reports:

| Kind | Required timing | Minimum content |
| --- | --- | --- |
| `start` | persisted and rendered before provider launch | identity, requested route, actual route, permission, resource budget |
| `state_change` | immediately after a durable state transition | prior/current state, concrete evidence, next action |
| `periodic` | no later than five minutes after the previous mandatory report | elapsed time, stage, last concrete evidence, liveness, resource state, next deadline |
| `attention` | immediately when operator input or intervention is required | reason, severity, allowed actions, deadline, retained evidence |
| `blocker` | immediately when forward progress is blocked without an immediate operator action | blocker, retryability, wake condition, next check |
| `terminal` | after process join and terminal persistence | outcome, evidence, delivery state, cleanup result, remaining attention |

Heartbeats and generic "still running" text are not concrete progress. The
periodic report states both semantic progress and process liveness, and it keeps
them distinct.

## Report Envelope

Every report uses a bounded envelope containing at least:

```json
{
  "schema": "loopcoder.ui.report.v1",
  "event_id": "event_...",
  "project_id": "project_...",
  "run_id": "run_...",
  "attempt_id": "attempt_...",
  "sequence": 42,
  "report_kind": "periodic",
  "stage": "worker_running",
  "status": "running",
  "elapsed_ms": 300000,
  "last_concrete_evidence": {},
  "requested_route": {},
  "actual_route": {},
  "resource_state": {},
  "attention": [],
  "blocker": null,
  "next_action": {},
  "next_report_at": "...",
  "recorded_at": "...",
  "privacy_class": "operator",
  "redaction": {},
  "content_digest": "sha256:..."
}
```

Unknown additive fields are ignored. Unknown schema major versions fail
explicitly. All strings, arrays, nested payloads, and rendered text have
documented limits. Absolute local paths, credentials, prompts, raw issue bodies,
private repository content, and raw provider output are excluded from the
default envelope.

## Human View Model

Human rendering is a projection of the envelope, never a second report truth.
The default compact view shows:

```text
run / issue / stage / elapsed
actual provider / model / effort / permission
last concrete evidence
process count / CPU / RSS / output state
attention or blocker
next action / next timeout / next report
```

Raw JSON, long logs, stack traces, and full evidence lists remain expandable or
available through explicit diagnostic commands. They are not dumped into the
primary report. Golden views cover narrow mobile-width surfaces and ordinary
desktop terminals without truncating identities, blockers, or required actions.

## Subscription And Replay

A client subscribes with a stable client identity, run or project filter,
capability declaration, and last acknowledged cursor. The core first replays
ordered durable reports after that cursor and then follows new reports.

Transport delivery is at least once. Semantic rendering is exactly once per
`(client_id, event_id, content_digest)`. Clients deduplicate by that tuple and
must not advance a cursor past a report they have not accepted.

A reconnecting client cannot cause provider restart, worker replay, duplicate
Git/GitHub side effects, or report regeneration. Slow clients use bounded queues;
overflow disconnects the client with a replayable cursor instead of blocking the
event writer or process supervisor.

## Delivery Acknowledgement

Delivery stages are monotonic and evidence-bearing:

| Stage | Meaning |
| --- | --- |
| `persisted` | authoritative event and report projection committed |
| `streamed` | bytes handed to a transport owned by LoopCoder |
| `accepted` | identified UI client accepted the complete envelope |
| `rendered` | UI client confirms the operator-visible representation was rendered |
| `seen` | UI provides an explicit user-observation acknowledgement |

`seen` is optional. `rendered` is mandatory for a UI to advertise full report
support. A terminal reference client may acknowledge `rendered` only after the
complete bounded report has been written successfully to its operator stream.

Acknowledgements include client ID, session ID, event ID, sequence, content
digest, stage, timestamp, adapter version, and bounded evidence. A stale,
regressive, mismatched, or cross-project acknowledgement is rejected.

## Mandatory Delivery Policy

At least one required report client must acknowledge the `start` report as
`rendered` before the provider process is launched. A requested UI mode that
cannot establish this proof fails closed before provider, worktree, or GitHub
side effects.

During execution:

- report generation continues even when a client disconnects;
- undelivered reports remain replayable;
- a fallback client may satisfy policy only if it proves its own rendering;
- one missed required acknowledgement produces `delivery_degraded` attention;
- two consecutive mandatory report intervals without any required `rendered`
  acknowledgement stop or detach according to an explicit run policy and return
  control to the operator;
- no policy may silently continue indefinitely while claiming successful UI
  reporting.

Delivery failure never prevents signal, join, descriptor close, reservation
release, or owned-worktree safety. It can block a clean product verdict until the
report obligation is resolved or explicitly waived by an authorized operator.

## Attention And Operator Actions

Attention is durable product state, not prose embedded in a progress line. An
attention item has stable identity, kind, severity, reason, allowed actions,
deadline, evidence references, created/acknowledged/resolved timestamps, and
resolution authority.

The v1 action set is intentionally small:

- acknowledge attention;
- supply bounded requested input;
- approve or deny a named permission transition;
- request cancel;
- request explicit detach;
- retry a provider-free stage;
- choose a documented recovery option.

Every action carries client/session identity, expected run revision, idempotency
key, and authorization evidence. A UI cannot mutate route pins, mark process
success, claim GitHub completion, bypass resource admission, or invent provider
state.

## Reference Transports

The protocol is transport-independent. v0.9.0 ships two required reference
transports:

1. **CLI JSONL/pretty transport.** `loopcoder events --run <id> --after
   <sequence> --follow` is the universal process/terminal integration. Machine
   JSONL and human rendering use separate output channels.
2. **Local HTTP and SSE transport.** An explicitly launched, run-bounded UI
   bridge exposes versioned JSON commands and an SSE report stream on loopback.
   It uses an ephemeral bearer capability, strict origin policy, bounded clients,
   and no credential or provider-token access.

The local bridge is not an always-on daemon. A UI or explicit LoopCoder run owns
its lifecycle. A future transport, including stdio JSON-RPC, WebSocket, MCP, or
operating-system notification, implements the same schemas and acknowledgement
semantics and does not change core lifecycle code.

## UI Capability Negotiation

A UI declares supported protocol versions, transports, report kinds, maximum
payload, acknowledgement stages, operator actions, rich-text/plain-text support,
and reconnect behavior. LoopCoder returns the effective capability set and any
degradation before execution.

Host or environment detection may suggest an adapter but never grants a
capability. Full integration is advertised only after an actual handshake and
conformance evidence. An unsupported UI degrades to a named reference transport
or fails closed when the user required that UI explicitly.

## Security And Privacy

- The loopback bridge binds only to loopback and requires an ephemeral scoped
  capability for every request.
- Client identity is not inferred solely from process environment variables.
- CORS/origin, request size, connection count, idle timeout, and output rate are
  deny-by-default and bounded.
- UI input is untrusted data and cannot alter immutable route, permission, base,
  project, or policy snapshots.
- Reports are redacted before persistence and again before client-specific
  rendering.
- Private project reports never enter machine-global logs or another project's
  subscriptions.
- External telemetry is disabled by default and is not required by the protocol.

## Conformance

The repository ships transport-neutral golden transcripts and a black-box UI
conformance runner. A UI can claim support only if it proves:

1. start, state-change, periodic, attention, blocker, and terminal rendering;
2. monotonic acknowledgement with honest `rendered` evidence;
3. disconnect/reconnect replay without loss or duplicate semantic rendering;
4. slow-consumer isolation and bounded resource use;
5. cancellation and attention actions through the one core lifecycle;
6. redaction and project isolation;
7. failure behavior when the UI is unavailable or rejects a report.

The terminal client is the reference implementation. Paseo is the first real
external conformance client, not a core dependency or privileged protocol. Codex,
Claude Code, and future UIs use the same suite and advertise only demonstrated
capabilities.

## Release Gate

v0.9.0 is not releasable unless the exact packaged artifact proves all of the
following without model-generated progress narration:

- one real execution renders every mandatory report through the terminal client;
- the same report sequence is consumed and acknowledged through the generic
  local UI bridge;
- a disconnect spanning at least one mandatory report replays correctly;
- a deliberately unavailable required UI fails or degrades exactly as declared;
- a twelve-minute silent worker remains visible at the mandatory cadence;
- cancellation joins every owned process and still renders a terminal report;
- one real external UI adapter, initially Paseo, passes the applicable public
  conformance profile;
- replacing that adapter with the conformance client requires no core change.
