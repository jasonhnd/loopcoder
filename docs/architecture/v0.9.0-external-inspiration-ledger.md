## Purpose

This ledger records the external projects studied for the v0.9.0 architecture,
the exact research revisions accepted by the roadmap, the behavioral ideas
LoopCoder may independently rewrite, the assumptions it rejects, and the review
checklist required before future inspired code merges.

This document is provenance only. It does not implement Work Graph, Provider
Plane, Router, Runtime, Supervisor, Delivery, Store and Events, or UI protocol
behavior. It also does not approve copying upstream source, schemas, tests,
fixtures, documentation prose, generated clients, prompts, or user-facing
names.

approved by this roadmap.

## Rewrite-Only Policy

LoopCoder may study public behavior, architecture, failure modes, and operator
contracts at the pinned revisions, then write LoopCoder-owned requirements,
interfaces, state transitions, events, tests, and documentation in LoopCoder
terminology through an independent Go rewrite.

LoopCoder must not:

- copy or line-by-line translate upstream source;
- port upstream schemas, tests, fixtures, prompts, generated clients, or prose;
- import upstream domain nouns as LoopCoder product concepts;
- imply upstream endorsement, partnership, certification, or compatibility; or
- treat a top-level MIT license as approval to copy dependencies, generated
  assets, vendored files, or later revisions without separate review.

Any future exception that proposes copied or ported material requires explicit
owner approval, license review, retained notices, isolated provenance, and any
required `THIRD_PARTY_NOTICES.md` update before merge. No such exception is
approved for v0.9.0.

## Adopted Ideas

### Gas City

| Adopted behavioral idea | LoopCoder location |
| --- | --- |
| Reconcile requested work with observed local execution instead of trusting callbacks alone. | Runtime and Supervisor components; future runtime/supervisor docs. |
| Keep work durable outside a single model conversation or host session. | Work Graph, Store and Events, and Delivery components; product charter authority rules. |
| Separate reusable workflow definitions from materialized execution attempts. | Work Graph and Delivery components; future work-graph docs. |
| Store lifecycle observations as immutable, ordered events replayable from a cursor. | Store and Events plus UI protocol components; event-stream and UI-report contracts. |
| Expose provider-neutral launch, liveness, stop, attach, log, adoption, and metadata contracts. | Runtime component; future provider-runtime docs. |
| Recover ambiguous live work only when ownership and process state are proven. | Supervisor and Delivery components; future recovery docs. |

Rejected assumptions:

- mandatory tmux, external issue databases, Dolt, repository mutation, or
  always-on local directories;
- unlimited fleets, role trees, autonomous scheduled orders, or idle patrol
  loops as default behavior;
- liveness that remains green while a provider process is blocked on operator
  input; and
- polling loops that create unbounded subprocesses, CPU use, wakeups, or
  battery drain.

### Gas Town

| Adopted behavioral idea | LoopCoder location |
| --- | --- |
| Keep persistent work identity separate from an ephemeral provider session. | Work Graph, Runtime, and Store and Events. |
| Re-derive patrol or recovery status from authoritative observations instead of trusting one heartbeat file. | Supervisor and recovery evidence. |
| Separate work execution from an ordered integration/commit queue. | Delivery and bounded workflow scheduling. |
| Make escalation and terminal ownership explicit. | Attempt state machine and operator-visible blockers. |

Rejected assumptions:

- liveness-over-safety recovery that may launch duplicate paid work;
- several competing heartbeat stores whose disagreement creates false stuck
  alerts;
- a fixed role taxonomy or always-running maintenance hierarchy; and
- tolerance for ambiguous duplicate execution in a single-user paid-provider
  workflow.

### Beads

| Adopted behavioral idea | LoopCoder location |
| --- | --- |
| Model dependencies so the ready set excludes work with open blockers. | Work Graph component; future work-graph docs. |
| Claim work and close work in guarded database transactions. | Work Graph and Store and Events components; future transaction docs. |
| Use stable work identity, idempotent replay, audit history, and explicit terminal states. | Work Graph, Store and Events, and Delivery components; product charter authority rules. |
| Keep integration-specific metadata extensible before making it permanent schema. | Store and Events component; future schema docs. |
| Compact old terminal execution detail while retaining provenance and final outcome. | Store and Events component; future retention docs. |

Rejected assumptions:

- Dolt as the default store, embedded/server Dolt lifecycle, remotes, branching,
  or merge semantics;
- repository-local task databases, identity files, hooks, or agent instruction
  mutation;
- a second GitHub issue source of truth or lossy bidirectional synchronization;
  and
- distributed multi-writer machinery for the default one-issue handoff path.

### Plexus

| Adopted behavioral idea | LoopCoder location |
| --- | --- |
| Track provider and model inventory with capability, freshness, confidence, and provenance. | Provider Plane component; future provider-inventory docs. |
| Represent quota windows with reset times plus unknown and stale states. | Provider Plane and Router components; future quota docs. |
| Persist health observations, classified failures, and bounded cooldowns. | Provider Plane and Router components; future health and routing docs. |
| Use ordered target groups and deterministic selection policies. | Router component; future routing docs. |
| Record request and attempt observations for latency, reliability, usage, and outcome. | Provider Plane, Runtime, and Store and Events components; future observation docs. |
| Classify stalls with hard timeouts rather than treating a connected process as progress. | Runtime and Supervisor components; future timeout docs. |

Rejected assumptions:

- a general provider HTTP translation proxy in v0.9.0;
- LoopCoder custody of provider secrets or a duplicate provider login UI;
- invisible request-by-request vendor switching inside one coding session;
- paid or quota-consuming background probes just to refresh rankings; and
- routing unsupported coding CLIs through a compatibility layer without
  end-to-end proof.

### Orca

| Adopted behavioral idea | LoopCoder location |
| --- | --- |
| Maintain normalized operator state separate from provider-process truth and UI rendering. | UI protocol, Runtime, and Store and Events components; product charter authority rules. |
| Combine process/PTY evidence with supported native agent hooks, falling back honestly when no structured UI surface exists. | Runtime, Supervisor, and UI protocol components; public UI-report contract. |
| Present current status, ordered events, attention notifications, and terminal result from one event stream. | UI protocol and Store and Events components; event-stream and UI-report contracts. |
| Fence completion and heartbeat evidence by task, dispatch, and execution identity. | Work Graph, Delivery, Runtime, and Store and Events components; future identity-fencing docs. |
| Keep transport keepalive separate from semantic progress. | Supervisor and UI protocol components; operational SLO and follow-stream contracts. |
| Preserve a client/control-plane boundary so a UI can display core-owned work without becoming execution truth. | UI protocol and Delivery components; public client boundary. |

Rejected assumptions:

- full IDE, editor, source-control UI, mobile client, SSH workspace manager,
  remote server, or parallel-agent fleet scope for v0.9.0;
- prompt-only heartbeat or `worker_done` messages as lifecycle truth;
- default permission bypass, silent unrestricted execution, or host-side
  mutation of LoopCoder policy;
- a competing host-owned orchestration database that races LoopCoder's
  event/attempt store; and
- host custody of provider credentials, token refresh, or undocumented quota
  access.

### CodexBar

| Adopted behavioral idea | LoopCoder location |
| --- | --- |
| Register providers through descriptors rather than central conditional chains. | Provider Plane adapter registry. |
| Give each provider an ordered fetch plan with explicit availability, source, strategy, diagnostics, and bounded fallback. | Provider snapshots and quota collectors. |
| Preserve the source and confidence of every quota observation. | Provider Plane and Router. |
| Adapt refresh cadence to active, warm, idle, power, and thermal state while capping coding-provider refresh frequency. | Provider refresh coordinator. |
| Bound subprocesses, network reads, redirects, output, and retries. | Runtime, Supervisor, and provider conformance tests. |

Rejected assumptions:

- importing Swift implementation or provider-specific private credentials;
- treating menu-bar display state as execution authority;
- unbounded polling to keep every provider value continuously fresh; and
- promoting an undocumented source to production authority merely because a UI
  can display it.

### Paseo

| Adopted behavioral idea | LoopCoder location |
| --- | --- |
| Keep a small explicit lifecycle (`initializing`, `idle`, `running`, `error`, `closed`) and derive aggregate attention separately. | UI protocol projections and conformance fixtures. |
| Keep parent lifecycle truth independent from provider-native child presentation. | Runtime and provider-native sub-agent containment. |
| Separate terminal activity transitions from workspace snapshots and notifications. | UI protocol final-mile delivery and status projection. |
| Use opt-in, fail-open hooks for presentation evidence without allowing hooks to own execution truth. | Optional UI client adapters. |
| Decompose large session code in behavior-preserving slices with boundary tests before movement. | v0.9 ordinary-development issue policy. |

Rejected assumptions:

- making Paseo a required runtime dependency or the only supported host;
- claiming in-session visibility from shell stderr that the host does not render;
- copying AGPL source, schemas, tests, fixtures, prose, or protocol names; and
- allowing host UI state or a provider-native child to close a LoopCoder
  attempt.

### Dolt

| Studied capability | v0.9.0 decision |
| --- | --- |
| Git-like branches, commits, diffs, merges, push, and pull for SQL tables. | Not required because cross-computer continuation occurs only after GitHub issue/PR completion. |
| MySQL-compatible client/server operation and embedded use through downstream products. | Rejected for the default local CLI because it adds server, connection, lifecycle, and recovery surface beyond the single-writer need. |
| Database remotes and multi-writer merge. | Reconsider only if concurrent offline writers to the same LoopCoder work database become a real requirement. |
| Versioned backup, migration, garbage collection, and integrity operations. | Use as design evidence for explicit lifecycle costs; do not adopt the dependency. |

The v0.9.0 storage choice remains pure-Go SQLite for machine-local authority and
GitHub for completed cross-computer handoff. This is a workload decision, not a
claim that SQLite is universally superior. Dolt would become objectively useful
if LoopCoder later needs concurrent, independently writable database histories
that must merge at the row/table level. That topology is explicitly absent from
the current user requirements.

## Provenance Review Checklist

Before merging future code or tests that claim external inspiration, reviewers
must confirm:

- the PR names the inspired behavior and points to this ledger or a later
  owner-approved ledger update;
- the implementation uses LoopCoder-owned packages, interfaces, state names,
  event names, tests, fixtures, and documentation prose;
- no upstream source, schemas, generated files, tests, fixtures, prompts, or
  documentation prose were copied or line-by-line translated;
- upstream project names are used only for attribution, not as LoopCoder domain
  nouns or user-facing concepts;
- the code stores authoritative execution truth in LoopCoder-owned state and
  does not introduce a competing external or host-owned control plane;
- license review is repeated for any file outside the pinned top-level project
  license, including dependencies, assets, vendored content, generated output,
  and later upstream revisions;
- any required attribution or notice update is present before merge;
- the PR stays inside its accepted issue and does not silently authorize future
  components; and
- ambiguous provenance, copied material, or license uncertainty is classified
  as `needs-human` rather than resolved by the worker.

## Future Updates

This ledger may change only through an explicit documentation issue or owner
correction. A future code PR may reference this document as provenance, but it
must not use that reference to expand scope beyond its accepted issue.
