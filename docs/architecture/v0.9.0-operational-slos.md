# v0.9.0 Operational SLOs

Status: draft
Roadmap ref: Phase R0 / R0.4 Operational SLOs
Issue: #1079
Stable ID: R0.4 Operational SLOs

## Purpose

This document defines the v0.9.0 operational report-delivery contract for Gate A
visibility and later gates. It is documentation only. It does not implement Host
Bridge, Supervisor, Runtime, Delivery, Store and Events, provider adapter, CLI,
schema, release, or packaging behavior.

The contract exists because persisted receipts that no active host renders are
not delivered progress. A v0.9.0 run must expose its current state, durable event
history, final-mile delivery evidence, bounded waits, retry budget, and duplicate
prevention rules in a way a terminal, Paseo, Codex, Claude Code, Orca, or future
host adapter can consume without becoming execution truth.

## Reporting Cadence

The mandatory cadence is attempt-start, state-change, terminal, and five-minute
semantic reports. Every active job attempt must emit semantic reports at these
points:

- attempt start, before provider execution or deterministic waiting begins;
- every consequential state change, including phase changes, blocker changes,
  retry decisions, stop requests, delivery transitions, CI/check transitions,
  verifier transitions, and human-gate transitions;
- terminal state, including success, failure, cancellation, timeout,
  needs-human, or superseded outcomes; and
- at least once every five minutes while the attempt is active, even when the
  only truthful report is that LoopCoder is waiting on an external system.

The five-minute receipt is a semantic progress obligation. It must summarize the
current phase, last evidence, next action, and any blocker. It must not be
satisfied by process liveness, provider token output, raw stderr, database
writes, or transport pings alone.

Transport keepalive is separate. A follow stream or host bridge may emit a
15-second keepalive to prove that the connection is still attached, but that
keepalive is not semantic progress, does not advance the current-status
projection, does not reset the five-minute report deadline, and must not be
displayed as an operator-visible progress report unless the host clearly labels
it as connection health.

## Versioned Report Fields

The authoritative machine contract is versioned JSON/JSONL. Pretty text may be
derived from it for humans, but pretty text is never parsed back as execution
state.

Every semantic event and current-status projection must carry this versioned
field set:

| Field | Requirement |
| --- | --- |
| `schema_version` | Required contract version for the event or projection. Unknown future versions must be handled by explicit compatibility policy, not silently parsed as the current contract. |
| `project` | Normalized GitHub host, owner, and repository identity. Local path aliases are not sufficient. |
| `job` | Stable work item identity for the requested issue or materialized workflow node. |
| `attempt` | Stable attempt identity for one bounded execution of the job. |
| `dispatch` | Stable dispatch identity for the selected provider/model/worktree route inside the attempt. |
| `sequence` | Monotonic per-run sequence number assigned when the durable event is accepted. |
| `occurred_at` | Occurrence time for the observed fact, recorded separately from write time when they differ. |
| `state` | Operator-visible lifecycle state, such as queued, running, waiting, blocked, stopping, succeeded, failed, cancelled, timed_out, or needs_human. |
| `phase` | Current phase within the state, such as intake, route, worktree, provider, local_check, delivery, ci_wait, verify, merge_gate, stop, or recovery. |
| `summary` | Bounded human summary of the current condition. The producer must keep it compact enough for repeated five-minute reports. |
| `last_evidence` | Bounded evidence pointer or short evidence list, such as process observation, file change, commit, PR, check, verifier result, host receipt, or deadline. |
| `next_action` | The next deterministic action LoopCoder expects to take, or the human/external action it is waiting for. |
| `blocker` | Nullable structured blocker reason when progress is waiting, unsafe, ambiguous, or needs a human decision. |
| `source` | Component that produced the event, such as runtime, supervisor, delivery, watcher, store, host_bridge, verifier, router, or operator. |

Events are immutable facts. The current-status projection is a compact,
replaceable view derived from the latest accepted events for the same
project/job/attempt/dispatch. A projection may omit historical detail, but it
must not invent state that is absent from the event stream.

`summary`, `last_evidence`, `next_action`, and `blocker` are bounded operator
fields, not raw logs. Provider transcripts, build logs, command output, and
stack traces remain local evidence unless a later contract explicitly publishes
a redacted excerpt.

## Final-Mile Delivery

Report delivery has five ordered final-mile stages:

| Stage | Meaning |
| --- | --- |
| `persisted` | LoopCoder durably accepted the event or current-status update into its local store. |
| `streamed` | LoopCoder wrote the event to the subscribed event stream after the subscriber's acknowledged cursor. |
| `host_accepted` | The host adapter acknowledged the event or receipt as accepted for rendering. |
| `rendered` | The host adapter proved that the receipt was presented in an operator-visible surface. |
| `seen` | The operator or host supplied an explicit acknowledgement that the rendered receipt was seen. |

Core and host adapters may claim only the highest stage they can prove. SQLite
writes, stderr writes, process output, local log files, relay records, and
internal host callbacks alone are not user-visible delivery. They may prove
`persisted` or `streamed`; they do not prove `rendered` or `seen`.

A report may be operationally successful at different stages depending on the
adapter. The generic terminal adapter is the reference human/machine adapter for
the stream. A real interactive-host adapter must prove at least `rendered` for
Gate A canaries before later gates may depend on host-visible reports.

Failed delivery must remain visible in state. A failed or downgraded host relay
must not block local process supervision, fabricate user visibility, or convert
an ambiguous provider or delivery state into success.

## Follow And Replay Cursor

The stable follow/replay surface is:

```text
loopcoder events --run <id> --after <seq> --follow --format jsonl
```

The command first replays durable events with `sequence > <seq>` in strict
ascending order, then follows new events as they are accepted. `--after 0`
means replay from the beginning of the run. The cursor is the highest sequence
number the client has durably processed or acknowledged, not the last line it
received on a socket.

Disconnect and restart behavior must be exactly-once from the client's
acknowledged cursor:

- a restarted client resumes with its last acknowledged `sequence`;
- the store replays every accepted event after that cursor before following
  live events;
- no accepted event after the cursor may be skipped;
- duplicate transport delivery before acknowledgement is tolerated, but clients
  deduplicate by `project`, `job`, `attempt`, `dispatch`, and `sequence`;
- a sequence number is never reused for a different event in the same run; and
- reconnect, host restart, watcher restart, or terminal attach must not invoke a
  model or repeat provider/GitHub side effects.

`loopcoder attach`, host integrations, and future readable status views must use
this event reader or a projection derived from the same ordered stream. They
must not create a second polling path with different delivery truth.

## Status Projection

`loopcoder status` reads the compact current projection for a run, job, attempt,
or project. It reports the latest accepted semantic state and the highest proven
final-mile stage. It is a read-only view over local execution truth plus
observed GitHub/provider evidence; it does not retry delivery, poll with a
model, or reinterpret stale provider prose as completion.

The projection must preserve enough identity to correlate with events:
`schema_version`, `project`, `job`, `attempt`, `dispatch`, latest `sequence`,
latest `occurred_at`, `state`, `phase`, bounded `summary`, `last_evidence`,
`next_action`, `blocker`, `source`, and highest proven delivery stage.

## Waits, Deadlines, And Stops

External waits are zero-model waits. CI, human approval, quota reset, retry
timers, delivery recovery, host reconnect, and scheduled polling are handled by
deterministic watchers that wake only on state change, deadline, or mandatory
five-minute semantic report. Waiting must not spend provider tokens or call a
model just to keep a run alive.

Every active attempt must have explicit deadlines for provider execution,
deterministic waits, graceful stop, and process join. A stop request must enter a
visible stopping phase, signal the owned process tree, wait only until the join
deadline, record remaining descendant evidence, and transition to a terminal
state if cleanup cannot complete. A process that remains connected but blocked
on input, stalled, or silent beyond the no-progress policy is not healthy
progress.

Deadline expiry is evidence. It must produce a state-change event and update the
current-status projection with the bounded reason, last evidence, and next
action. It must not be hidden behind an unchanged running state.

## Resource Ceilings

The default v0.9.0 path is bounded to one top-level worker attempt for one issue
and one PR. The verifier does not run concurrently with the worker on the same
local host, and provider-native sub-agents are disabled unless a later accepted
policy explicitly admits them inside the parent attempt's supervised process
tree and resource budget.

Each job admission must name ceilings for:

- active top-level workers, verifiers, local test jobs, and descendant
  processes;
- provider/model route and quota window;
- wall-clock attempt duration and deterministic wait duration;
- CPU, RSS, and process-tree ownership;
- local focused checks versus remote heavy gates; and
- delivery retry and host-relay retry behavior.

Ceiling denial is a visible operational state, not silent queue starvation.
Denials must emit a bounded report with the responsible policy, current usage,
and next action.

## Issue Duration And Retry Budget

Every issue must be scoped so one worker can complete the primary behavior in a
bounded attempt. Roadmap slices should fit the documented 30-90 minute worker
execution target; if intake cannot explain why a slice fits, the work is split
before dispatch rather than after a timeout.

A failed stage receives at most one automatic scoped retry after the failure is
classified. Retryable failures include transient network/provider outages with
no public side effects. `needs-human` covers ambiguity that conflicts with the
accepted roadmap or unclear external side effects. `terminal-fail` covers code
changes in documentation-only work, scope expansion, or repeated failure after
the retry budget is exhausted.

Retry resumes the failed stage only. It must not repeat successful provider
execution, duplicate commits, open duplicate PRs, post duplicate comments, rerun
an already successful verifier, or spend model tokens for CI/approval/relay
waiting. When side effects are ambiguous, LoopCoder stops for human review
instead of replaying the action.

## Duplicate Prevention

Provider execution, branch creation, commit creation, PR creation, issue
commenting, verifier execution, merge, release, and report delivery are
idempotent stages with durable evidence. A restarted run or resumed watcher must
read the existing evidence and continue from the next incomplete stage.

No duplicate PR or duplicate provider execution is allowed merely because a
host disconnected, a watcher restarted, a report failed to render, CI was still
pending, or the operator reattached from an old cursor. Report delivery failure
is repaired through the event cursor and final-mile acknowledgement contract,
not by repeating work that already produced public or provider side effects.

## Scope Boundaries

This document defines the operational SLO contract for later implementation
slices. It does not activate R0.3, R0.5, R1, R5.7, R6.6, or any Host Bridge,
Supervisor, Runtime, Delivery, Store and Events, provider, release, or packaging
code. Future code PRs must cite the accepted document they implement and stay
inside their own roadmap slice.
