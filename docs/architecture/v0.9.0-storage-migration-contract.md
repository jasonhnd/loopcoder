# v0.9.0 Storage/migration Contract

Status: development-ready retained v0.9.0 contract; owner acceptance required
Historical roadmap ref: Phase R1 / R1.2 Storage/migration contract
Historical source issue: #1085
Historical stable ID: R1.2 Storage/migration contract

## Purpose

This document defines the v0.9.0 storage and migration contract for LoopCoder
durable local state. It describes the compact schema responsibilities, migration
and compatibility rules, owner-only permission requirements, integrity checks,
and ownership destinations for later implementation slices.

This is documentation only. It does not implement SQLite schema DDL, migrations,
Go packages, CLI commands, runtime behavior, dispatch, verification, release
logic, or activation of later R1 slices.

The durable nouns and transitions come from
[`v0.9.0-domain-state-contract.md`](v0.9.0-domain-state-contract.md). UI client
cursors, acknowledgements, Attention, and action receipts implement the public
[`v0.9.0 UI report protocol`](v0.9.0-ui-report-protocol.md) and its
[`operational SLOs`](v0.9.0-operational-slos.md).

## Storage Boundary

LoopCoder storage is machine-local runtime state. It preserves enough durable
truth for a single local operator to recover Work Graph, Job, Attempt, Event,
provider, route, delivery, and UI-report state after a UI disconnect,
process restart, or binary upgrade.

The store is authoritative only for local LoopCoder state. It is not
authoritative for GitHub repository truth, provider credentials, provider quota,
remote CI, merge approval, release approval, or user-visible rendering that a
named UI client cannot prove.

All durable and transient LoopCoder-owned state remains outside repositories
under the configured LoopCoder home. The target topology is:

- `$LOOPCODER_HOME/data/machine.db` for machine authority: project aliases,
  provider/model/quota observations, cooldowns, and global resource admission;
- `$LOOPCODER_HOME/projects/<project-id>/project.db` for one project's work,
  attempt, event, route, delivery, UI-client cursor, acknowledgement, Attention,
  and action-receipt state; and
- `$LOOPCODER_HOME/projects/<project-id>/{runs,logs,tmp,recovery}` for bounded
  project-scoped payloads.

Customer repositories and their worktrees must contain no LoopCoder database,
run sidecar, relay queue, recovery file, log, temporary file, or hidden
`.loopcoder` directory. A repository may contain an explicitly user-authored,
reviewable project policy file, but runtime operation must not mutate it.

The storage contract must not introduce:

- a competing UI-owned orchestration database;
- a repository-local source of truth for LoopCoder work state;
- a replacement for GitHub issues, PRs, branches, checks, reviews, labels, or
  release gates;
- a provider credential vault or copied provider account database;
- distributed multi-writer replication for one in-flight issue;
- a general analytics warehouse or unbounded transcript archive; or
- a schema that requires old v0.8 internal tables to remain public contracts.

## Compact Schema Responsibilities

The compact schema is the durable local substrate for the v0.9.0 contracts. It
must store normalized identities, immutable events, compact current projections,
idempotency records, migration history, and bounded evidence pointers. It should
keep hot status reads small while preserving enough history to replay state and
classify authority disagreements honestly.

The schema is responsible for these durable records:

| Record family | Responsibility |
| --- | --- |
| Store metadata | Database identity, schema version, created time, last successful migration, compatibility floor, and local store format identity. |
| Project identity | Normalized GitHub host, owner, repository, local aliases, and last observed repository evidence. |
| Work Graph | WorkItem projections, Dependencies, readiness state, claim state, owner, lease epoch, and terminal outcome evidence. |
| Jobs and Attempts | Local Job admission, selected Provider/Model route, worktree boundary, process ownership summary, deadlines, retry budget, and terminal evidence. |
| Events | Immutable ordered facts with idempotency key, subject identity, source surface, accepted sequence, occurrence time, bounded evidence pointer, and optional redacted summary. |
| Current projections | Replaceable status views derived from Events for project, WorkItem, Job, Attempt, Gate, Provider, Model, route, UI delivery, and Attention state. |
| Provider Plane | Non-secret provider and model snapshots, capability observations, health observations, quota freshness, confidence, and provenance. |
| Router | Deterministic route decisions, policy inputs, selected route, denial reasons, cooldowns, and usage windows. |
| Delivery | Branch, commit, PR, check, verifier, merge-gate, and release-gate projections plus evidence pointers to GitHub or local verifier output. |
| UI protocol | UI client identity and capability, required/optional subscription policy, follow cursor, final-mile acknowledgement, Attention lifecycle, authorized action receipt, and replay checkpoint. |
| Idempotency | Operation keys, normalized payload digests, accepted result identities, conflict records, and side-effect completion markers. |
| Migration ledger | Applied migration versions, checksums or identifiers, apply time, source and target versions, backup manifest pointers, and verification result. |

The schema must not store provider secrets, raw tokens, private keys, unbounded
provider transcripts, unbounded build logs, or repository-visible copies of
local-only Worker, Verifier, or Conductor report payloads. It may store redacted
summaries and local evidence pointers when later readers can still classify the
state without exposing secrets.

Current projections are caches. They may be replaced during replay, compaction,
or repair, but they must not invent a state transition that is absent from the
accepted event stream or from a fresh owning authority read.

## Event And Projection Rules

Events are append-only local facts accepted by Store and Events. Every accepted
event must have one monotonic local sequence within its project or run scope,
one idempotency key, one subject, one source surface, and one bounded evidence
pointer or redacted summary.

Projection updates must be derived from accepted Events and fresh authority
reads. A projection may collapse old detail, but it must preserve:

- the latest schema and projection version it was built from;
- enough entity identity to correlate with Events;
- the latest accepted sequence or authority observation used;
- the current state, phase, blocker, and terminal outcome when present; and
- the evidence pointer that justified the projection.

Projection compaction must keep terminal provenance. Deleting raw transient
detail is allowed only when the retained Event, final state, evidence pointer,
and authority surface are sufficient to explain why the entity is done, failed,
cancelled, timed out, superseded, or needs human attention.

## Migration Versioning

The store has one monotonically increasing schema version recorded inside the
database. Each migration version represents one accepted storage shape change
and must be recorded in the migration ledger after it succeeds.

Migration versioning rules:

- Versions advance only forward.
- Each version has one stable identifier and one deterministic migration body.
- The migration ledger must be contiguous from the database's creation version
  through its current version.
- A migration must be idempotent for an already-applied version and must detect
  same-version payload drift as an integrity conflict.
- A database newer than the running binary must fail closed before mutation.
- A database with missing, reordered, duplicated, or conflicting migration
  ledger entries must fail closed before mutation.
- Schema version constants are implementation details; command output may expose
  source and target versions, but user-facing docs should describe behavior
  instead of depending on table names.

Reader-facing JSON or JSONL contracts, such as event streams or migration plans,
must carry their own contract version. Unknown future fields may be ignored only
where that reader contract explicitly allows it. Unknown future schema versions
in the SQLite store must not be silently opened as current.

## Migration Planning

Planning is the default migration mode and is side-effect-free. A migration plan
must open the existing database read-only, verify its basic integrity, read its
metadata and migration ledger, classify the source and target versions, and
report the ordered steps needed to reach the running binary's target version.

A plan must not create a database, parent directory, backup directory, WAL file,
or migration record. It must not change permissions. It must not run provider,
GitHub, verifier, host, merge, or release side effects.

The plan result must classify at least:

| Status | Meaning |
| --- | --- |
| `fresh` | No existing database is present and initialization would be required by a later explicit write path. |
| `current` | The database is already at the running binary's target schema version and passes read-only validation. |
| `upgrade-required` | A supported older schema can be migrated to the running binary's target version. |
| `unsupported-old` | The source version is older than the compatibility floor for this binary. |
| `unsupported-new` | The source version is newer than this binary understands. |
| `invalid` | Integrity, permission, file-type, path, or migration-ledger validation failed. |

Only `current` and `upgrade-required` are eligible for a later apply step.
`fresh` is eligible only for a separate explicit initialization path. All other
statuses require operator-visible diagnosis and no mutation.

## Migration Apply

Apply is explicit and mutating. It must use the same Store and Events engine that
normal LoopCoder commands use, not a separate script with different lock,
permission, transaction, or integrity behavior.

An apply operation must:

1. verify owner-only path, directory, database, WAL, SHM, and backup
   permissions before opening for write;
2. acquire exclusive local migration ownership so no other LoopCoder process can
   write the store concurrently;
3. compute the read-only plan again and verify that source, target, and step
   fingerprint still match the reviewed plan when a reviewed plan is supplied;
4. create a verified owner-only backup before any destructive or incompatible
   schema change;
5. apply all required migration versions in order inside a bounded transaction
   sequence that cannot mark the target version successful until every required
   step and post-check succeeds;
6. update the migration ledger with the stable migration identity and applied
   result;
7. reopen the migrated database read-only and run integrity, ledger, foreign-key
   or relationship, projection, and required-table checks; and
8. verify the backup manifest, digest, owner-only permissions, and path
   confinement before reporting success.

Re-running apply against an already-current database is an idempotent no-op. It
must not create duplicate backups, duplicate migration ledger entries, duplicate
events, duplicate GitHub mutations, duplicate provider attempts, duplicate PRs,
or duplicate UI reports.

If apply fails before a target version is fully verified, the database must not
claim that target version. The failure must leave enough evidence to diagnose
whether the live database was unchanged, transaction-rolled-back, or needs
offline operator review.

## Compatibility Constraints

The v0.9.0 storage implementation may migrate from only the explicitly supported
legacy versions named by later code slices and release notes. Support for a
legacy schema means the binary can plan, back up, migrate, and verify that
schema; it does not mean the old schema remains a public API.

Compatibility constraints:

- A newer binary may open an older supported schema only through the migration
  planner or an explicit apply path.
- An older binary must fail closed on a newer schema and must not attempt best
  effort reads.
- A fresh machine should be able to continue completed work from GitHub evidence
  without copying another machine's SQLite database.
- In-flight local work is owned by the machine that holds the local claim and
  process evidence; copying the database to another machine is not a supported
  handoff mechanism.
- Patch releases may add backward-compatible reader fields, but must not require
  a hidden schema mutation during read-only commands.
- Minor storage upgrades that change durable semantics require a documented
  migration path, rollback limitation notes, and release evidence.
- Removing legacy fields or compacting old detail is allowed only when retained
  Events and evidence pointers still satisfy the v0.9.0 domain/state and
  operational SLO contracts.

Rollback is not an automatic normal command unless a later accepted contract
defines it. Replacing a live SQLite database can mix restored files with active
WAL/SHM state, local claims, process ownership, or UI cursors. Any rollback
procedure must be offline, owner-visible, backup-preserving, and explicit about
state written after the backup.

## Permissions And Local Authority

Storage files are local-only runtime data. The database, WAL, SHM, backups,
manifests, run records, and recovery sidecars must not be committed, attached to
issues, copied into PR bodies, or published as release artifacts.

Owner-only permission expectations:

| Path class | Required expectation |
| --- | --- |
| LoopCoder home and `data` directory | Owned by the current user and not group- or world-writable. |
| Database, WAL, SHM, backup, and manifest files | Owned by the current user and readable/writable only by that user. |
| Parent directories | Not symlinks that escape the accepted LoopCoder home and not writable by other users. |
| Backup directories | Owner-only, path-confined below the accepted data directory unless an explicit absolute backup path passes the same checks. |

The store must reject or fail closed on unsafe symlinks, non-regular database
paths, owner mismatch, group/world-writable files, path traversal, unreadable
metadata, corrupt SQLite integrity, missing migration ledger entries, and
conflicting idempotency payloads.

Permission checks protect local authority, not secrecy from the operating
system owner. They do not make the database safe for publishing, syncing through
untrusted services, or sharing across accounts.

## Integrity Expectations

Every write path that changes durable state must preserve idempotency,
transactional consistency, and replayability. A crash, UI disconnect, retry,
or duplicate command invocation must resume from accepted evidence instead of
repeating provider execution or external side effects.

Integrity checks must cover:

- SQLite integrity and relationship constraints;
- contiguous migration ledger history;
- schema metadata matching the migration ledger;
- uniqueness of normalized Project, WorkItem, Job, Attempt, Event, Gate,
  Provider, Model, route, and idempotency identities;
- no second active Job claim for the same WorkItem unless a later accepted
  bounded workflow contract permits distinct visible child WorkItems;
- projection sequence pointers that refer to accepted Events or fresh authority
  observations;
- backup digest and manifest consistency; and
- local-only report and transcript redaction boundaries.

Integrity failure is a visible blocked or `needs_human` condition. Store and
Events must not silently repair ambiguous history by deleting events, rewriting
terminal states, stealing claims, or trusting provider prose over local evidence.

## Later Implementation Destinations

Later code slices may implement this contract in these component destinations:

| Destination | Later responsibility |
| --- | --- |
| Store and Events | Database open, metadata, migrations, idempotency, immutable event acceptance, projection rebuild, integrity checks, and backup manifests. |
| Work Graph | Project, WorkItem, Dependency, readiness, claim, and terminal projection storage. |
| Runtime and Supervisor | Job, Attempt, process ownership, timeout, stop, and process-evidence storage. |
| Provider Plane | Provider/model inventory, capability, quota, health, freshness, confidence, and provenance snapshots. |
| Router | Route policy inputs, selected route records, denials, cooldowns, and deterministic replay of route decisions. |
| Delivery | Branch, commit, PR, check, verifier, merge-gate, and release-gate evidence projections. |
| UI protocol | Report projection, client capability, event follow cursors, final-mile acknowledgement, Attention, authorized action receipts, and replay checkpoints. |
| CLI and diagnostics | Read-only plan/status/doctor surfaces plus explicit apply surfaces that use Store and Events rather than separate migration logic. |
| Release and packaging | Upgrade smoke, migration fixtures, backup verification, rollback limitation evidence, and compatibility release notes. |

These destinations are architectural ownership boundaries, not package names,
table names, or permission to implement code in this documentation slice. Future
implementation PRs must cite this accepted contract and stay inside their own
roadmap slice.

## Scope Boundaries

This contract is an architecture input for later ordinary-development issues. It
does not:

- implement schema DDL, migrations, storage adapters, CLI commands, tests, or
  release automation;
- change the current v0.8 storage migration reference;
- authorize Work Graph, Store and Events, Runtime, Supervisor, Provider Plane,
  Router, Delivery, UI bridge, or release behavior;
- create a UI-side or repository-side database;
- define a public SQLite table API for external tools; or
- publish additional issues or dependencies.

The accepted contract becomes the storage and migration design boundary for
future v0.9.0 implementation issues.
