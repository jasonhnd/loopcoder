# v0.9.0 Product Charter

Status: development-ready retained v0.9.0 contract; owner acceptance required
Historical roadmap ref: `phase-r0-charter-provenance-and-measurable-baseline/doc-1`
Historical source issue: #1066
Historical stable ID: R0.1 Product charter

## Purpose

This charter defines the v0.9.0 product boundary before new runtime work starts.
It is documentation only. It does not implement Work Graph, Provider Plane,
Router, Runtime, Supervisor, Delivery, migration, or release behavior.

v0.9.0 is a controlled replacement and consolidation of LoopCoder's core path.
The product must first become reliable for one developer running LoopCoder on a
native macOS Apple Silicon computer, working across local public or private
GitHub repositories, and using provider accounts and subscriptions they already
own. Larger autonomous fleets, multi-computer in-flight orchestration, and
silent decomposition are outside the default product.

## Development Method

v0.9.0 is developed as an ordinary software project. LoopCoder is the product
under construction, not the controller that develops itself. A human developer
or an explicitly selected external coding agent may implement one accepted
GitHub issue in a normal branch or worktree and open a PR against `pre-prod`.
The v0.8.1 binary is a supported predecessor and migration fixture only; it is
not authorized to compile this roadmap, create issues, dispatch workers, choose
models, activate slices, merge PRs, or supervise v0.9 development.

This boundary remains in force until v0.9.0 is production-usable and the owner
separately approves a future self-development experiment. Self-bootstrap is not
a v0.9.0 release gate. Product acceptance uses disposable consumer repositories
and deterministic provider fixtures so a defect in the product cannot corrupt
the mechanism being used to repair it.

Development rules are conventional and explicit:

- GitHub milestone and issue state track planned and completed work; roadmap
  markers never create or activate work.
- The owner chooses the developer or coding agent and, when applicable, its
  provider, model, and effort. The development process must not substitute a
  different model silently.
- Each implementation issue changes one primary behavior, has no more than five
  acceptance criteria, and targets one PR that an ordinary developer can finish
  in no more than two working days.
- Local verification is limited to formatting, compilation, and focused tests.
  Full test, race, static-analysis, security, packaging, and release evidence is
  produced once at its owning remote boundary.
- Greptile or another optional review bot may add evidence, but its absence is
  not a required merge gate unless repository protection is deliberately
  changed in a separate owner-approved decision.
- No development issue launches LoopCoder, calls `loopcoder compile`, uses an
  active-slice marker, or runs a provider through LoopCoder.

## Primary User

The primary user is one developer on macOS Apple Silicon who wants a quiet,
bounded delivery tool for a single GitHub issue at a time.

That user should not need to reason about internal protocol surfaces such as
ready-set scheduling, dispatch waves, state branches, provider-native child
ownership, relay cursors, or old v0.8 compatibility machinery in the default
path. The default path must explain the current issue, selected provider/model,
worktree, progress, CI state, verifier result, and human decision point.

## Default Workflow

The default v0.9.0 workflow is:

```text
GitHub issue
  -> one bounded local job
  -> one selected provider/model
  -> one top-level worker attempt
  -> one worktree
  -> one pull request
  -> remote CI
  -> independent verification
  -> explicit human merge or configured release gate
```

`loopcoder run <issue>` is the intended primary command for this path. The
default is deliberately small:

- one GitHub issue, one top-level worker attempt, one worktree, and one PR;
- one selected provider/model pinned for the whole attempt;
- no verifier running concurrently with the worker on the same local host;
- no model calls while waiting for CI, approval, quota reset, or scheduled
  retry;
- focused local checks only when needed for the current change; and
- full repository test, race, static analysis, security, install, upgrade, and
  release matrices on remote CI.

Provider-native sub-agents, when a provider exposes them and policy permits
them, remain inside the selected parent attempt, supervised process tree,
write boundary, and resource budget. They cannot independently own GitHub
issues, branches, PRs, merges, release actions, or LoopCoder task truth.

## Ownership Boundaries

LoopCoder owns the local development-delivery control plane. That means it owns
the v0.9 domain model, Go interfaces, persistence schema, routing policy,
process lifecycle, supervision, reports, tests, compatibility policy, and
official provider adapters.

External research provenance is tracked in
[`v0.9.0-external-inspiration-ledger.md`](v0.9.0-external-inspiration-ledger.md).
That ledger records the accepted pins, rewrite-only policy, adopted ideas, and
rejected assumptions for the public projects studied by the roadmap.
Operational report-delivery SLOs are defined in
[`v0.9.0-operational-slos.md`](v0.9.0-operational-slos.md).
The public UI/report, acknowledgement, attention, and operator-action contract
is defined in
[`v0.9.0-ui-report-protocol.md`](v0.9.0-ui-report-protocol.md).
The v0.9.0 domain nouns, state transitions, idempotency rules, and
source-of-truth boundaries are defined in
[`v0.9.0-domain-state-contract.md`](v0.9.0-domain-state-contract.md).

GitHub owns collaboration and delivery truth. Issues, PRs, branches, commits,
reviews, labels, and hosted checks are the synchronization surface between
computers and collaborators. A completed issue or PR can be continued from a
new computer through GitHub alone; in-flight local scheduler databases are not
replicated or merged across computers.

Local SQLite owns current local execution state. A small machine-authority store
records project aliases, provider/model/quota observations, cooldowns, and
machine-wide resource reservations. A separate project store records that
project's work items, dependencies, jobs, attempts, events, route decisions,
delivery evidence, UI client cursors and acknowledgements, attention, and
operator-action receipts. Both live under `$LOOPCODER_HOME`; neither
lives in a customer repository. They are authoritative for the current
machine's observed execution, but they do not replace GitHub as the delivery
source of truth.
The v0.9.0 storage and migration boundary is defined in
[`v0.9.0-storage-migration-contract.md`](v0.9.0-storage-migration-contract.md).

Provider systems own credentials, account state, and quota authority.
LoopCoder may discover executables, probe non-secret auth readiness, cache
bounded provider snapshots, and record observed usage, but it does not custody
provider secrets or fabricate quota where a provider exposes no authoritative
source.

## Authority Rules

- Requested work, collaboration, and completion:
  GitHub issue, PR, check, and review state are authoritative. Local chat
  transcripts and local task caches are not delivery truth.
- Cross-computer continuation:
  Completed GitHub issue, PR, and commit history are authoritative. A new
  computer creates fresh local execution state instead of merging copied SQLite
  files.
- Current local execution:
  Local SQLite job, attempt, and event records plus observed process state are
  authoritative. Provider prose or self-report alone cannot mark local work
  complete.
- User-visible reporting:
  the public `loopcoder.ui.v1` envelope, durable client cursor, and the highest
  acknowledgement stage a named UI can prove are authoritative. Persistence,
  stderr, logs, transport writes, and generic host detection do not prove that
  the user received a report. A required report is delivered only at
  `rendered` or `seen`.
- Code changes:
  The Git commit and PR head are authoritative. Worker prose saying work is
  complete is not enough.
- Merge and release eligibility:
  Configured remote CI, the independent verifier, and the explicit gate are
  authoritative. Worker exit code alone cannot make a PR merge-eligible.
- Provider credentials and account ownership:
  The provider CLI, keychain, or auth system is authoritative. LoopCoder's
  database must not become a credential vault.
- Provider quota:
  Fresh provider-authoritative evidence is authoritative when available.
  Guessed values and LoopCoder-observed usage alone are not authoritative quota.

LoopCoder may create local worktrees, run supervised provider attempts, capture
changes, create PRs, read remote checks, run an independent verifier, and report
the resulting evidence. It must fail closed to `needs-human` when authority is
ambiguous: unknown provider execution, unreadable verification evidence, stale
approvals, missing required checks, or unclear external side effects do not
become success.

Human merge remains the default production authority unless a project has an
explicit configured release gate. Automatic production merge or release is not
part of the default v0.9.0 charter.

## Default Mode And Bounded Workflow Mode

LoopCoder is headless and UI-neutral. The terminal is the reference UI, a local
loopback HTTP/SSE bridge is the generic integration surface, and Paseo is the
first external conformance client. Paseo, Codex, Claude Code, editors, and
future clients receive no privileged execution API and never own local run
truth. A provider must not launch until at least one required client renders the
attempt-start report. Missed mandatory reporting creates durable attention and
the immutable run policy decides bounded stop or explicit detach; silent
continuation is not healthy operation.

Default mode is the one-issue, one-worker, one-PR path. It is the first product
path that must become reliable before breadth is optimized.

Bounded workflow mode is an explicit advanced mode. It may later materialize a
small dependency graph only after an operator-visible plan and approval. It is
not silently selected by the scheduler, router, provider, or host integration.
The initial production bounds are depth <= 3, fan-out <= 3, and active
top-level workers <= 1 by default. Provider-native parallelism remains
separately bounded inside the parent process tree.

Workflow child work, when explicitly enabled, must be represented as visible
Work Graph nodes with their own claims, attempts, resource budgets, and merge
boundaries. Provider-native children are never a substitute for LoopCoder-owned
work truth.

## v0.9.0 Non-goals

The v0.9.0 roadmap explicitly excludes:

- Reimplementing or embedding Dolt.
- Shipping a clone of Gas City, Beads, or Plexus under different names.
- General-purpose issue tracking, team chat, provider API gateway, credential
  vault, dashboard, Kubernetes fleet, Windows/Linux support, or mobile control.
- Multiple computers concurrently orchestrating one in-flight issue.
- Unlimited autonomous agents, silent model decomposition, or random provider
  exploration.
- Automatic production merge/release without the configured human gate.
- Maintaining every v0.8 internal API or database table indefinitely.
- Claiming authoritative quota where the provider exposes none.
- Optimizing breadth before the one-worker direct path is proven reliable.
- Requiring Paseo or any other single UI in order to run, inspect, stop, or
  recover LoopCoder.

These non-goals constrain v0.9.0 scope. Later roadmap slices may document
specific mechanisms, but they must not reinterpret this charter as approval to
expand the default product beyond the one-worker direct path.
